INPUT CONTRACT:
The input below is a single JSON object describing:

- target_package: the exact Java package this page object must be declared in.
- customqa_constraints: the platform's own SonarQube customqa:* quality-profile rules this page object must never violate. Every constraint listed here is a hard requirement, not a suggestion.
- methods: a non-empty, ordered list of every action this class must support. Each entry has:

  - action_text: a plain description of the page action this method must support (e.g. "click the forgot password link").
  - captures: an ordered list of the action's own required parameters, each with a Cucumber Expression type (e.g. "string", "int") or null for an untyped capture -- this method's own parameters must correspond to these, in order.
  - return_type: the EXACT Java return type this method must declare (e.g. "boolean", "void", "String"), already derived by the platform from how the calling step definition actually uses this method's result -- or `null` when no such usage could be derived, in which case you choose whichever return type is idiomatic for the action.

RETURN-TYPE CONTRACT (read this before writing any method whose `return_type` is non-null):
- The calling step definition already exists and its own code was inspected to produce `return_type` -- it tells you exactly what the caller does with this method's result. Declaring anything else will not compile against that already-generated caller.
- `return_type: "boolean"` means the caller wraps this call directly in `Assertions.assertTrue(...)` or `Assertions.assertFalse(...)` (or assigns it to a `boolean` variable). The method must `return` a `boolean` value it computes itself (e.g. `return wait.until(ExpectedConditions.visibilityOfElementLocated(locator)) != null;` or a try/catch around a lookup that returns `false` on failure) -- it must NOT throw or otherwise substitute an internal assertion for returning the value; the caller is the one asserting.
- `return_type: "void"` means the caller invokes this method as a bare statement and never uses a result. The method may (and, for a verification action, should) perform its own waiting and throw/self-assert internally (e.g. via `wait.until(...)`, which already throws `TimeoutException` on failure) -- it must NOT declare a non-void return type nobody will read.
- `return_type` for any other value (e.g. "String", "int") means the caller assigns this call's result to a variable of that declared type -- the method must return a value of exactly that type.
- `return_type: null` (or omitted): no constraint -- choose whichever return-type convention (boolean-returning query vs. void self-asserting action) is idiomatic for this specific action, exactly as you would without this section.
- This constraint applies ONLY to the method's declared return type and its own `return` statements -- it changes nothing about the CONSTRAINTS section below, still non-negotiable.

BASEPAGE'S REAL INHERITED API (the COMPLETE list -- this class extends BasePage, so every one of these is already available; nothing else is):
- `protected final WebDriver driver` -- the injected WebDriver for this screen. Use it directly (e.g. `driver.findElement(locator)`) for any interaction BasePage itself does not provide a method for.
- `protected final WebDriverWait wait` -- an explicit wait already constructed against `driver` with the platform's configured timeout. Use it directly (e.g. `wait.until(...)`) for any explicit-wait interaction; never construct a second `WebDriverWait`.
- `public void open(String url)` -- navigates `driver` to `url`.
- `public String currentTitle()` -- returns `driver`'s current page title.
This is the ENTIRE inherited surface. BasePage does NOT provide `isElementDisplayed`, `sendKeys`, `click`, `findElement`, `getText`, or any other convenience helper -- do not call a BasePage method that is not in this list. For any locator interaction not covered by `open`/`currentTitle`, use this class's own `driver`/`wait` fields with Selenium's own `WebElement`/`By` API directly (e.g. `driver.findElement(locator).click()`, `wait.until(ExpectedConditions.visibilityOfElementLocated(locator))`) -- never assume BasePage exposes a shortcut for it.

CONSTRAINTS (from the platform's customqa:* quality profile -- non-negotiable):
