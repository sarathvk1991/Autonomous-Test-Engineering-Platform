# ADR-0045 — Scoped Asset Promotion (Layer 3 Capstone, pulled from Layer 4)

- **Status:** Accepted
- **Date:** 2026-07-30
- **Supersedes:** nothing. **Amends:** ADR-0037 (Generated Test Suite Target and SUT Binding — resolves its long-open promotion TBD; additive amendment notes added beneath the "Two-tier split, locked" decision text, the promotion TBD bullet, and Recommendation 4 — see ADR-0037 for the added text; this ADR is the "future ADR" ADR-0037's own Recommendation 4 already anticipated as the only sanctioned way to revisit "never automatic"). ADR-0040 (Control Point Model and Layer 4 Redefinition — additive: records the scope boundary between this ADR's promotion decision and Layer 4's suite-level integration governance remit, so a reader does not mistake this ADR as pulling Layer 4's broader governance forward too; an inline note is added near Decision 3 — see ADR-0040 for the added text. No existing ADR-0040 decision changes.)
- **Governing design:** none. Evidentiary basis: ADR-0037 (the promotion TBD's own text and the "explicit, reviewed step" language it locked); ADR-0044 (D3's persistent, tracked-baseline-reconciled catalog; D4's three-part reuse-safety model and its confidence/content-hash/signature-fit identity mechanism; D5/D6's CP3/CP4 gate shapes); ADR-0040 (Decision 3's Layer 4 suite-level integration governance list, the remit this ADR pulls promotion forward from without pulling the rest of).
- **Depends on:** ADR-0037 (the TBD this ADR resolves, the tracked-baseline/per-run-workspace split promotion moves assets between, the SUT-binding boundary promoted test-data classes must still respect); ADR-0044 (D3's catalog and D4's reuse-safety identity mechanism, reused here rather than duplicated; D5/D6's CP3/CP4 gates, which this ADR's D2 makes a promotion precondition; D8's own note that promotion is "now more motivated" because the catalog cannot grow without it); ADR-0040 (Decision 3's Layer 4 remit, whose boundary with this ADR is D1, below).
- **Runtime status:** Not applicable. This is a **pure, documentation-only decision lock** — it builds no code, defines no schema, and creates no directory. It authorizes a future Layer 3 implementation milestone (the capstone step, D4) to build a promotion mechanism against the decisions locked here, exactly as ADR-0037 and ADR-0044 already authorize the rest of Layer 3 without building it themselves.

## Problem

ADR-0037 locked, on 2026-07-24, that "promotion from workspace to baseline is an explicit, reviewed step — never automatic," and left "the exact promotion review mechanism (human approval, a governed gate, or both)" as an open TBD. ADR-0044 (2026-07-29), freezing Layer 3's own architecture, could not resolve that TBD itself — it explicitly records promotion as remaining "ADR-0037's own open TBD" (D8, Consequences, Ownership) — but it also sharpened why leaving it open is no longer merely an unresolved detail: Layer 3's reuse catalog (ADR-0044 D3) is a **persistent** store, reconciled against the tracked baseline at the start of each run, not rebuilt from a per-run workspace. An asset a run generates lands only in that run's untracked workspace (ADR-0037's per-run workspace); unless it is promoted into the tracked baseline before the next run starts, the next run's catalog reconciliation has nothing new to find. Reuse — the entire differentiator ADR-0044 D3 locks as Layer 3's "core generation discipline" — cannot accumulate across runs without a promotion mechanism existing. ADR-0044 states this plainly: promotion is "now more motivated... since promotion is also how the reuse catalog... actually grows."

ADR-0040 Decision 3 assigns Layer 4 "suite-level integration governance" broadly, and the promotion TBD has, until now, sat unassigned to any specific layer's build order. Because Layer 3's own reuse catalog structurally depends on promotion existing — not on Layer 4's broader suite-governance remit, which depends on nothing Layer 3 builds — this ADR pulls **only** the promotion decision forward from where it would otherwise land (a future Layer 4 build) into Layer 3's own capstone, resolving ADR-0037's TBD now rather than leaving Layer 3's reuse discipline structurally inert until Layer 4 exists.

## Decision

### D1 — Scope: promotion only, not Layer 4's broader remit

This ADR resolves **only** promotion — the workspace → tracked-baseline transition ADR-0037 named. It does **not** pull forward any of Layer 4's other suite-level integration governance (ADR-0040 Decision 3):

- orphaned-glue detection ("every step definition resolves to at least one scenario")
- cross-suite near-duplicate analysis — i.e., "no near-duplicate step definitions across the suite" as a *whole-suite* sweep, which is a broader check than D2(b)'s promotion-time anti-duplicate gate below (D2(b) checks one candidate asset against the tracked baseline; Layer 4's check sweeps the entire assembled suite for near-duplicates regardless of promotion history)
- the aggregate release gate ("aggregate policy gate and the release decision on the suite as a whole")

All three remain Layer 4's, unchanged from ADR-0040 Decision 3, and are not built, specified, or authorized by this ADR.

Promotion is pulled forward specifically because Layer 3's reuse catalog (ADR-0044 D3) cannot grow without it: an asset generated in run N only becomes reusable catalog content in run N+1 if it is promoted into the tracked baseline the catalog reconciles from at the start of every run (ADR-0044 D3, "reconciled against a scan of the tracked baseline's committed Java... at the start of each run"). Without promotion, every run's catalog reconciliation finds exactly what the last promotion left behind — nothing, if promotion has never run — and reuse stays permanently at the bootstrap 0% ADR-0044 D5 already names as correct for a run with an empty catalog, never advancing past it. Layer 4's other governance checks (orphaned glue, suite-wide near-duplicates, the release gate) have no equivalent dependency pulling them into Layer 3; they remain exactly where ADR-0040 placed them.

**This is designed to be wrapped, not replaced.** Layer 4, once built, may wrap this promotion decision in richer suite-level governance — for example, folding a promotion event into its own aggregate release gate, or extending its cross-suite near-duplicate sweep to also re-verify recently-promoted assets. Nothing in this ADR forecloses that. What this ADR locks is the minimum promotion decision Layer 3 needs to function as a reuse-accumulating system; it is not a claim that promotion can never be governed more richly later.

**Amendment note (additive, 2026-08-06, ADR-0046).** This anticipated wrapping is now designed and locked: ADR-0046 (Layer 4 Quality Governance Architecture Freeze) specifies CP5's own promotion-wrapping component as a suite-level gate that runs AFTER this ADR's own per-asset promotion stages a candidate (`git add`, never `git commit` — D5, unchanged) and BEFORE that staged change becomes a commit, reusing `reconcile()`'s working-tree read to see the assembled post-staging state with no new plumbing. A CP5 suite-level rejection of an individually-clean, D2/D3-passing asset routes into this ADR's own D3 shared human review queue — not a second, CP5-specific one — extending, not amending, D3's "one review queue, not two" discipline. This ADR's own D1–D5 are unchanged by ADR-0046; it wraps them, per D1's own anticipation, and does not re-litigate what's promotable or the review model (Recommendation 4, unchanged).

### D2 — Promotable gate

A workspace asset auto-promotes into the tracked baseline when **both** of the following hold:

**(a) Per-asset validation passed.** The asset's owning feature passed CP2 (ADR-0043's Gherkin lint + feature governance gate), and the asset's own automation passed CP3 (ADR-0044 D5 — step/scenario coverage, zero unmapped/duplicate steps, and the hard SonarQube `customqa:*` quality-gate scan) and CP4 (ADR-0044 D6 — static locator health: uniqueness, no duplicate locators, dynamic-XPath thresholds, well-formedness). An asset whose feature or automation has not cleared every gate its layer already owns is not promotion-eligible, regardless of (b).

**(b) Confirmed not a duplicate of an existing tracked-baseline asset.** "Duplicate" is defined using the **same identity mechanism ADR-0044 D3/D4 already computes for reuse matching** — this ADR invents no second duplicate-detection mechanism. A candidate is a duplicate when an entry already exists in the tracked baseline keyed to the same identity: the content-hash ADR-0044 D4(b) already validates catalog entries against, and the step-definition signature/parameter shape ADR-0044 D4(c) already checks for fit. Concretely: before promoting, the candidate's own (content-hash, signature) pair is checked against the reconciled catalog (ADR-0044 D3) exactly as a reuse MATCH lookup would be — if that lookup would have returned a trusted binding (ADR-0044 D4(a)+(b)+(c), all three), the candidate is a duplicate of what the catalog already describes and does not promote as new content. This is the one suite-level check promotion structurally requires: without it, every run that generates an asset the catalog's own reuse discipline should have found instead accumulates a redundant near-copy in the tracked baseline, degrading reuse (and inflating the catalog) on every subsequent run.

Both (a) and (b) are computed from artifacts Layer 3 already produces — the CP3 and CP4 validation reports (ADR-0044 D1) and the reuse engine's own identity computation (ADR-0044 D3/D4) — no new validation surface is introduced.

> **Additive note (2026-08-06): the promotion gate moves from WHOLE-RUN to PER-ASSET.** D2(a)'s own text above ("the asset's own automation passed CP3 and CP4") was implemented, until this note, at the granularity CP3/CP4 are actually computed at — ONE shared verdict per run, applied to every candidate alike (`AssetGateOutcomes`'s own pre-note docstring: "neither gate is computed per individual asset in this platform yet"). A live confirming run exposed the resulting gap directly: 30 clean binds/generates promoted 0, because 30 OTHER needs in the SAME batch escalated, which failed CP3's whole-run coverage criteria, which failed the run's shared `Cp3Result.overall_verdict`, which — via the one shared `AssetGateOutcomes` every candidate was gated against — blocked EVERY candidate, the 30 clean ones included. This is not what D2(a) itself requires; D2(a) asks whether THIS asset's own automation passed CP3/CP4, and a candidate whose own class has no problem should not be blocked by a DIFFERENT need's own failure to resolve.
>
> **Resolved: an asset promotes iff (1) its own per-asset criteria pass (the static customqa checks against ITS OWN generated code; the non-duplicate check, D2(b), unchanged and already per-candidate) AND (2) it is part of the cleanly-resolved, correctly-mapped set (a `Generated*`/`Bound*` outcome — an `Escalated*` outcome never reaches this gate at all, D3, unchanged) AND (3) the batch-level criteria that GENUINELY apply uniformly to every candidate pass (today: the whole-project Sonar quality gate, and CP4's own whole-batch locator-health sweep) — and, critically, ANOTHER need in the same run escalating, or a DIFFERENT class's own criteria failing, does NOT block this candidate.**
>
> This is a granularity change to HOW D2(a) is evaluated, not a change to WHAT D2(a) requires — CP2, CP3, and CP4 are all still required to pass for a candidate to promote (Recommendation 1, unchanged); D2(b)'s non-duplicate check, D3's review model, and D5's stage-for-review mechanism are all unchanged. The one substantive constraint this note is honest about: SonarQube's own `/api/qualitygates/project_status` reports ONE verdict for the whole scanned Maven project, with no file/class attribution (`SonarQualityGateResult`/`SonarQualityGateCondition`, `cp3/sonar/models.py`) — there is no way to honestly ask "did THIS class's code pass Sonar" separately from "did the whole project's code pass Sonar" given the real machinery this platform has today. A whole-project Sonar FAIL therefore still blocks every candidate in the batch, exactly as before this note; what changed is that coverage/escalation-driven CP3 failures (the three coverage criteria) and the two static customqa checks (which DO carry real per-class attribution) no longer conflate with Sonar's own genuinely-batch verdict. Built in `automation_engineering/promotion/cp3_decomposition.py` (`decompose_for_asset`) and wired through `AssetGateOutcomes.first_failure` (now `class_name`/`asset_id`-scoped) and `evaluate_promotion` (`automation_engineering/promotion/gate.py`, `automation_engineering/promotion/models.py`). See ADR-0044 D5's own companion additive note (this same date) for the CP3-specific decomposition this note depends on. Proven against the exact confirming-run scenario: `tests/unit/test_automation_engineering_stage.py::TestPerAssetPromotionAcrossEscalations` (a mixed batch — clean generates plus an unrelated escalation — promotes the clean ones; the escalated one does not, and does not block the others) and `tests/unit/test_automation_engineering_promotion_gate.py::TestPerAssetCp3Decomposition` (a per-class/per-asset criterion failing for one class/asset does not block a different one; the whole-project Sonar criterion still blocks everyone).

### D3 — Review model

Assets that satisfy both D2(a) and D2(b) **auto-promote** — no additional human review gates a clean, validated, confirmed-non-duplicate asset's promotion.

Anything the reuse engine **escalated** under ADR-0044 D4 — low match confidence (D4(a)), a content-hash-stale catalog entry (D4(b)), or a signature/parameter mismatch (D4(c)) — does **not** auto-promote, whether or not its CP3/CP4 gates independently passed. It waits for the same human-in-the-loop review ADR-0044 D4 already triggers for that escalation. **Promotion escalation and reuse escalation are the same review, not two separate ones**: an asset that reached D4's escalation path never had a trusted reuse binding to begin with, so a human is already in the loop deciding what to do with it before promotion becomes a question at all; this ADR does not add a second, parallel review queue for the same event.

This reconciles ADR-0037's "explicit, reviewed step" language (D1, above, and the amendment note added to ADR-0037 alongside this ADR): review is required for exactly the cases where judgment is actually load-bearing — ADR-0044 D4's escalations, the one Layer 3 failure mode "invisible to every deterministic downstream gate" (ADR-0044 D4's own rationale) — not for every clean, validated, non-duplicate asset. Requiring a human to re-review an asset that has already cleared CP2, CP3, CP4, and the D2(b) duplicate check would bottleneck the catalog growth that is promotion's entire purpose (Problem, above), for no additional safety: nothing about human re-review would catch a failure mode CP2–CP4 and the duplicate check do not already catch, since D2(b) already reuses the one check (D4's three-part identity test) that catches the failure mode CP3/CP4 structurally cannot see.

**If a future implementer or reviewer instead decides every promotion — clean or escalated — must pass human review**, that is a valid, more conservative alternative this ADR explicitly did not choose, and adopting it requires a future ADR amending this decision, not a silent implementation choice; this ADR's own D3 is the auto-promote-on-clean-pass model, stated as the locked decision, not the only conceivable one.

### D4 — Sequencing

Promotion is the **last** Layer 3 build step — its capstone. It depends on CP3 and CP4 already existing (a gate cannot be evaluated before it is built), and the reuse catalog (ADR-0044 D3) depends on promotion to grow at all (Problem, above). Build order, locked:

**catalog → reuse engine → generators → CP3 → CP4 → promotion.**

Every step before promotion runs against an empty or still-growing catalog and reuses 0% of its steps — correctly, not as a failure, exactly as ADR-0044 D5 already establishes for the bootstrap run. Promotion is what converts that correct-but-inert 0% into a system that actually accumulates reuse across runs; nothing before it can do so, by construction.

Promotion's move **into** Layer 3 (from where it would otherwise land, a future Layer 4 build, per ADR-0040 Decision 3's original broader remit) is a scope shift, and this ADR is the record of it: Layer 3's build order now ends with promotion rather than ending at CP4 and deferring promotion entirely to Layer 4's own future architecture.

### D5 — Mechanism (high-level)

Promotion **copies** validated, non-duplicate assets (D2) from the run's untracked workspace (ADR-0037's per-run workspace, "Path A") into the tracked baseline, producing a **git-visible change** — unlike the workspace's own disposable output, a promoted asset is tracked, versioned, and persists past the run that produced it. That persistence is the entire point: it is what the reuse catalog reconciles against on the next run (ADR-0044 D3).

**Whether promotion auto-commits the resulting change or stages it for a separate review/merge step is a mechanism TBD, deferred to implementation** (Consequences, below). What is locked here is the **decision** — what is promotable (D2), and the review model governing it (D3) — not the exact git mechanics of how the copy becomes a committed change. An implementation may auto-commit, may open a pull request, or may stage the change for a separate CI gate to merge; any of these satisfies this ADR's decision as long as it does not re-introduce human review for assets D3 already designates as auto-promoting, and does not bypass human review for assets D3 designates as requiring it.

> **Additive implementation note (2026-08-02).** D5's mechanism TBD is resolved: **stage-for-review**, never auto-commit. `automation_engineering/promotion/mechanism.py::apply_promotion` writes a promoted candidate's Java source into the tracked baseline; `stage_promoted_assets` runs `git add` on the written file and never calls `git commit`. Rationale: D3 and D5 answer different questions — D3 is whether the *promotion decision* needs a human (it doesn't, for a clean, D2-passing asset); D5 is whether the resulting *git history* needs one before it becomes a commit. ADR-0037's original "explicit, reviewed step" language was about a human having eyes on a tracked-baseline change before it lands, not about re-litigating D2/D3's own safety judgment — auto-promoting a clean asset does not imply auto-committing it. This choice costs nothing structurally: `automation_engineering.catalog.scanner.reconcile` reads the working tree directly, not git's index or commit history, so a staged-but-uncommitted promoted asset is already visible to the very next run's catalog reconciliation — proven end to end (run 1 promotes and stages, without committing; run 2's reconciliation finds the asset and the reuse engine trusts it) in `tests/unit/test_automation_engineering_promotion_loop.py`. This satisfies D5's own acceptance criterion: it neither re-introduces review for a D3 auto-promoting asset (the promotion decision itself still requires no human) nor bypasses review for one D3 requires it for (an escalated asset, per D3, is never even resolved to a candidate, let alone staged).

## Consequences

- ADR-0037's promotion TBD is resolved: the promotable gate (D2), the review model (D3), the build-order placement (D4), and the mechanism's decision-vs-implementation split (D5) are all locked. ADR-0037's own "never automatic" Decision text (its "Two-tier split, locked" section) is narrowed, not reversed, by D3: promotion is no longer categorically manual, but escalated assets still receive exactly the explicit, reviewed step ADR-0037 originally required for all promotions — see the amendment note added to ADR-0037 alongside this ADR.
- **What stays Layer 4's, untouched by this ADR:** everything named in D1's exclusion list — orphaned-glue detection, the suite-wide near-duplicate sweep (broader than D2(b)'s single-asset check), and the aggregate release gate (ADR-0040 Decision 3). Layer 4's future architecture-freeze ADR may still wrap this ADR's promotion decision in richer governance (D1); it is not required to, and this ADR does not anticipate what form that wrapping would take.
- **ADR-0044's own "does not own... the promotion mechanism" language (its Consequences and Ownership sections) is superseded by this ADR's own Acceptance, not silently left standing:** at ADR-0044's own Acceptance (2026-07-29), promotion was correctly recorded as unresolved and outside Layer 3's locked scope. This ADR is the resolution ADR-0044 D8 anticipated ("this ADR does not resolve the promotion mechanism; it records why resolving it is now more consequential than before") — promotion is now Layer 3's own capstone (D4, above). ADR-0044's body is not edited by this ADR (the same non-retroactive-editing discipline this repository already applies to Accepted ADR bodies elsewhere); this note reconciles the two documents for a reader moving from one to the other, the same reconciliation pattern ADR-0044 D5 already used for the ADR-0037/ADR-0040 "Layer 4 asset" tension.
- ~~The promotion mechanism's exact form — auto-commit vs. stage-for-review, and the precise git operation used — is **TBD-at-implementation** (D5).~~ **Resolved (2026-08-02): stage-for-review** (`git add`, never `git commit`) — see the additive note beneath D5.
- **Resolved (2026-08-06): the promotion gate's own granularity is per-asset, not whole-run** — see the additive note beneath D2. A candidate's own CP3/CP4 gate outcome no longer collapses into one shared, whole-batch verdict for every candidate; a clean asset promotes even when an unrelated need in the same run escalates or a different candidate's own criteria fail.
- The asset catalog's exact storage location (ADR-0044 D3's own separate TBD) is unaffected by this ADR and remains open, resolved at implementation when the catalog is first built against a real filesystem layout.

## Recommendations (permanent)

1. **No promotion mechanism, once implemented, may auto-promote an asset that failed CP2, CP3, or CP4, or that the reuse engine escalated under ADR-0044 D4** — D2 and D3 are both required, every time; passing D2(a) alone, or D2(b) alone, is not sufficient.
2. **Promotion escalation and reuse escalation must remain one review queue, not two** — a future implementation that builds a second, promotion-specific escalation path alongside ADR-0044 D4's own reuse-escalation path violates D3's central decision.
3. **No new duplicate-detection mechanism is ever built for promotion** — D2(b) reuses ADR-0044 D3/D4's own content-hash and signature identity computation; a future implementation that adds a second, independent duplicate check for promotion specifically violates D2's own text.
4. **Layer 4's future architecture-freeze ADR must not re-litigate what's promotable or the review model** (D2/D3) — it may wrap promotion in richer suite-level governance (D1), but the promotable gate and review model are this ADR's decision, not Layer 4's to redecide without a future ADR amending this one.

## Ownership, scope, and governance

- **Owns:** the promotion decision in full — the promotable gate (D2), the review model distinguishing auto-promotion from escalation-triggered human review (D3), promotion's sequencing as Layer 3's capstone build step (D4), and the decision/mechanism split for how the workspace-to-baseline copy is realized (D5).
- **Does not own:** Layer 4's suite-level integration governance beyond the single-asset anti-duplicate check D2(b) reuses (D1) — orphaned-glue detection, the suite-wide near-duplicate sweep, and the aggregate release gate remain ADR-0040 Decision 3's; the reuse catalog's own storage location or semantic-match mechanism (ADR-0044 D3's own TBDs, unaffected); CP3's and CP4's own rule catalogues (ADR-0044 D5/D6, unchanged — this ADR only makes their passing a promotion precondition); the exact git mechanics of the promotion mechanism itself (D5, TBD-at-implementation).
- **Governance:** Accepted, effective immediately. Amends ADR-0037 additively (resolves its promotion TBD; see ADR-0037's own added notes) and ADR-0040 additively (records the scope boundary with Layer 4; see ADR-0040's own added note). Supersedes neither. Authorizes a future Layer 3 implementation milestone to build the promotion mechanism against D1–D5 without redesigning them.
