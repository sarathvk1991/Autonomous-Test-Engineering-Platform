## Problem

ADR-0040 Decision 3 names Layer 4's remit — suite-level integration governance: orphaned-glue detection, no near-duplicate step definitions across the suite, the assembled suite compiles, and the aggregate policy gate / release decision — and ADR-0044 confirms this is specifically CP5, with CP6 belonging to Layer 5's own execution concern. Neither ADR designs CP5 in the detail an implementation needs; ADR-0045 D1 explicitly preserved that gap, pulling forward only per-asset promotion and stating the rest — "orphaned-glue detection... cross-suite near-duplicate analysis... the aggregate release gate... All three remain Layer 4's... This is designed to be wrapped, not replaced."

Two documents were produced to close that gap. First, a transcription-plus-review of the `Quality_Governance_Layer.pptx` deck (`docs/proposals/layer-4-quality-governance-lld.md`), which found the deck's own content real but its labels wrong: the deck calls its whole-suite Sonar governance "CP5" and its execution-readiness governance "CP6," both of which collide with ADR-0040/ADR-0044's already-Accepted assignment of those exact labels to different content (CP5 = suite-integration governance; CP6 = Layer 5's execution control point). Second, a design proposal for the real CP5 (`docs/proposals/layer-4-cp5-suite-integration-governance-design.md`), which designed all four items ADR-0040 Decision 3 names, reusing the catalog, the reuse engine's semantic matcher, the Gherkin-needs derivation, and the per-asset promotion mechanism ADR-0044/ADR-0045 already built — and surfaced eight decisions still open at the design stage.

This ADR resolves both gaps: it renumbers the deck's mislabeled concerns to non-colliding control points (D1) and locks the CP5 design's eight open decisions as binding Decision text (D2–D6), the same two-part freeze pattern ADR-0043 and ADR-0044 each already applied to their own layer's LLD.

## Decision

### D1 — Scope and control-point numbering (resolves the LLD's Finding 0)

Layer 4 (Suite Quality Governance) comprises **three** control points, not the deck's two, correctly numbered against what ADR-0040/ADR-0044 already claimed:

| Control point | Owning layer | Content | This ADR's disposition |
|---|---|---|---|
| CP5 | Layer 4 | Suite-integration governance (orphaned-glue detection, cross-suite near-duplicate sweep, promotion-wrapping, aggregate-release cohesion) | **Fully designed and locked here** (D2–D6) |
| CP6 | Layer 5 | Execution (ADR-0044's own confirmed assignment) | **Unchanged, not owned by this ADR** — restated only for the numbering table's own completeness |
| CP7 | Layer 4 | Suite-wide quality (Sonar) governance — the deck's mislabeled "CP5" | **Named and scoped only** (D8) — detailed design deferred to a future task |
| CP8 | Layer 4 | Static execution-readiness governance — the deck's mislabeled static-half "CP6" | **Named and scoped only** (D8) — detailed design deferred to a future task |

The deck's *dynamic* execution-readiness content (build succeeds, smoke test passes — its own "CP6" other half) is **not a Layer 4 control point under any number** — it is Layer 5's own execution concern, folding into Layer 5's existing CP6 or a Layer-5-owned sub-check, per the same static/live boundary CP4 already drew (ADR-0044 D6) and the LLD review's own S2 finding.

**Why CP7/CP8, not CP6-and-a-half or a renumbered CP5/CP6.** ADR-0044 already claims CP6 for Layer 5, Accepted, before this ADR exists — this ADR cannot retroactively reassign it without amending ADR-0044's own Decision text, which it does not do (Recommendation, below). The next unclaimed numbers in the sequence are CP7 and CP8. **This produces a numbering-order / pipeline-order mismatch, stated honestly rather than hidden:** CP7 (suite quality) and CP8 (execution readiness) both logically gate a suite *before* Layer 5's CP6 (execution) ever runs, yet carry higher numbers. This is a cosmetic consequence of control points being locked incrementally, one ADR at a time, rather than reserved as a numbered block up front — nothing in this platform's control-point machinery requires CP numbers to be monotonic with pipeline order (CP3 and CP4 already both belong to Layer 3, non-monotonic with Layer 4/5's own single control points either side of them). No renumbering of CP1–CP6 is proposed or authorized here.

**Governance reporting is not a fourth control point.** Layer 4 produces CP5/CP7/CP8 validation reports and a consolidated governance report set (D9, below); it does not itself render a dashboard — that remains Layer 7's job (ADR-0031), restated as binding here per the LLD review's own S4 finding.

### D2 — CP5, orphaned-glue detection: deterministic primary check, semantic advisory only

An orphaned step definition is one referenced by **no step in the current, whole tracked feature corpus** — every `.feature` file the tracked baseline carries, not merely the run's own newly generated ones. This is a suite-scope determination by construction; no per-run, Layer-3-scoped check can answer it, which is exactly why it is Layer 4's and not Layer 3's (ADR-0044 D1's own scope boundary, restated).

**Primary determination is deterministic pattern-vs-literal-text matching, not semantic similarity.** Cucumber itself resolves glue at runtime by matching a step's literal text against a step definition's own pattern (a Cucumber Expression or regex) — never by semantic similarity. A step definition orphaned by this deterministic check will genuinely never fire at execution time, regardless of how semantically "similar" its own intent reads to some current need. This keeps orphan detection a genuine, deterministic contributor to CP5's own gate, consistent with ADR-0040 Decision 2 ("control-point gates evaluate only deterministic evidence... LLM-generated assessments are advisory only... never gate"). The evaluator itself (a Cucumber Expression/regex matcher over the catalog's already-recorded `pattern` field and the needs-derivation's already-recorded `text` field) does not exist in this codebase today and is new build work, deferred to implementation (Consequences, below) — this Decision locks what it must do, not its code.

**Semantic similarity is a secondary, advisory-only hint** — a pattern-orphaned asset that scores highly similar to some current need (using the same embedding machinery D3 reuses) may be flagged as "possibly a broken pattern, not dead code" for human attention, but never overrides or substitutes for the deterministic determination, and never by itself changes orphan status.

**Action on a detected orphan: flag for human review, never auto-remove.** Deleting glue code is destructive and, unlike promotion's own additive, staged changes, not naturally reversible via a diff a human can decline. An orphan detector with a false positive (a needs-derivation gap, a pattern-matcher defect) that auto-deleted would silently break a still-wanted binding with nothing staged for a human to catch first. This mirrors ADR-0045 D3's own posture — automate only what is provably safe by construction; escalate everything else to the one shared human review queue (D4, below).

### D3 — CP5, cross-suite near-duplicate sweep: step-definitions only, reused embedding machinery, 0.90 default threshold

The sweep is scoped to **step definitions only**, matching both ADR-0040 Decision 3's own literal text ("no near-duplicate step definitions across the suite") and `LiveSemanticMatcher`'s existing implementation scope (`automation_engineering/reuse/live_matcher.py`'s own docstring: "Only step definitions are matched"). This alignment is reported, not silently assumed: extending the sweep to page objects or utilities would require both new embedding-text derivation for those asset kinds (none exists today) and an amendment to ADR-0040 Decision 3's own text — neither is authorized here.

**Distinct from ADR-0045 D2(b), stated precisely.** D2(b) is an exact, content-hash duplicate check, performed per candidate, at promotion time, against the tracked baseline — it catches byte-identical re-promotion only. This sweep is semantic, suite-wide, and retrospective: it finds clusters of step definitions that are each individually content-hash-unique (so D2(b) correctly let each one promote on its own run) but express near-identical intent, most plausibly because independent generation across different runs solved the same need slightly differently.

**Mechanism: reuse the embedding boundary's existing one-batched-call shape, never rebuild it.** `EmbeddingProvider.embed()` (`automation_engineering/reuse/embeddings.py`) already embeds many texts in one call; `LiveSemanticMatcher.prime()` already demonstrates the pattern (embed once, compare many times in memory). CP5's sweep embeds every catalogued step-definition's text once (one batched call, or a bounded few per the provider's own batching), then computes the full pairwise cosine-similarity matrix in memory — no further network calls. `_cosine_similarity` and `_embedding_text` (currently private to `live_matcher.py`) are **promoted to a shared, public location** for this second consumer, mirroring the `method_shape_fits` precedent already established in this codebase (originally private to `reuse/engine.py`, promoted to public specifically so `generation/method_fit.py` could reuse the identical rule rather than hand-maintain a second copy) — locked here as the required pattern, not left to independent implementation choice.

**Cluster threshold: default 0.90, configurable, anchored to real calibration data already on record.** `reuse/engine.py`'s own `DEFAULT_GENERATE_FLOOR`/`DEFAULT_CONFIDENCE_THRESHOLD` docstrings record real, live-measured scores against this platform's embedding model: unrelated text `[0.5196, 0.6688]`, a full paraphrase of an existing pattern `0.8980`, an exact-text match `0.9843`. `0.90` sits a small, explicit margin above the measured paraphrase floor. Cosine similarity is symmetric regardless of which side of a comparison is labeled "need" and which "catalog asset," so this need-vs-asset calibration is valid evidence for an asset-vs-asset comparison using the identical model and identical `_embedding_text` shaping. **This is a locked default, not a locked constant** — real calibration against actual observed near-duplicate pairs (which this platform has not yet collected, unlike the paraphrase/exact bands) should confirm or tune it at implementation; the threshold is configurable for exactly this reason, mirroring `confidence_threshold`'s own pre-existing configurability in the reuse engine.

**Action: flag the cluster for human consolidation review, never auto-merge.** Auto-merging automation code requires deciding which implementation is canonical and rewriting every current Gherkin binding that depended on the discarded copy — a consequential, code-editing decision no deterministic gate makes unattended. Same posture as D2's orphan action.

**Cost, recorded so a future implementer does not over-engineer against a scale that does not exist.** The embedding **API cost is O(1) batched calls**, not O(n); the **O(n²) cost is purely in-memory arithmetic** over already-fetched vectors, no network, no additional API quota. At this repository's real current scale (34 step-definition-bearing files, confirmed directly for the design proposal this Decision locks) this is a non-issue. A future implementer facing catalog growth into the thousands may bucket by `semantic_tags` before pairwise comparison — noted as a future optimization trigger, not required now.

### D4 — CP5, promotion-wrapping: after staging, before commit, one shared review queue

CP5 is the suite-level gate ADR-0045 D1 anticipated wrapping the per-asset promotion mechanism it built (`automation_engineering/promotion/`, closed end-to-end 2026-08-02): an asset that passed per-asset promotion (ADR-0045 D2's own CP2+CP3+CP4-pass, non-duplicate gate) can still be rejected at suite level because it orphans existing glue, joins a near-duplicate cluster (D3), or breaks aggregate cohesion (D5).

**Wrap order: CP5 runs after per-asset promotion stages (`git add`, never `git commit` — ADR-0045 D5, unchanged), and before whatever turns that staged change into a commit.** This exploits, rather than duplicates, a property ADR-0045's own mechanism already establishes: `scanner.reconcile()` reads the working tree directly, not git's index or commit history — the loop-closing proof (`tests/unit/test_automation_engineering_promotion_loop.py`) already demonstrates a staged-but-uncommitted promoted asset is visible to the very next reconciliation. CP5 needs no new plumbing to see the assembled post-staging state: a second `reconcile()` call, run moments after staging, already sees it. ADR-0045 D5's own text anticipates exactly this shape — "An implementation may... stage the change for a separate CI gate to merge" — and CP5 is that gate.

**A suite-level reject leaves the staged diff exactly as promotion left it — untouched, visible, unresolved.** CP5 never `git restore`s or unstages a rejected change and never forces a decision; it routes the finding to review. This preserves ADR-0045 D5's "a human has eyes on a tracked-baseline change before it lands" posture rather than re-deciding it on a human's behalf.

**Routing: the same shared human review queue ADR-0045 D3 already established — not a third, CP5-specific queue.** ADR-0045 D3/Recommendation 2 already lock "promotion escalation and reuse escalation are the same review, not two separate ones." A CP5 suite-level rejection of an otherwise individually-clean asset is, structurally, the same shape: a human must decide something no deterministic per-asset check could catch. This Decision extends that one-queue discipline to CP5's own findings rather than opening a second review lane.

**This does not re-litigate ADR-0045 D2/D3 — it wraps them, unchanged**, per ADR-0045's own Recommendation 4 ("Layer 4's future architecture-freeze ADR must not re-litigate what's promotable or the review model").

### D5 — CP5, aggregate-release cohesion: compile is Layer 4, run is Layer 5; exact-collision ambiguous-glue v1

**The compile boundary is the same live-tool-but-not-live-SUT line CP3/CP4 already drew, applied consistently.** ADR-0044 D5 already establishes that a Layer 3/4-owned gate may depend on live *tooling infrastructure* (a running SonarQube server) without crossing into Layer 5's territory; ADR-0044 D6 draws the actual forbidden boundary at a **SUT or browser** dependency, not any live dependency whatsoever ("No running browser and no SUT are consulted... Live-DOM validation... is explicitly not CP4's job. That is Layer 5's runtime concern"). Invoking a JDK/Maven toolchain to compile the assembled suite is the same kind of dependency as CP3's Sonar server — a build-time tool call, never a SUT or browser — so it is consistently Layer 4's, not Layer 5's. **Locked: "does the assembled suite compile" is CP5's own check** (`test-suite-baseline/pom.xml`, confirmed present, is the build artifact this check invokes against). "Does it then successfully run" (a smoke test passing) remains Layer 5's, unchanged, per the LLD review's own S2 finding and this same static/live boundary.

**Ambiguous-glue detection, v1: exact pattern-string collision across distinct classes.** Cucumber raises an "Ambiguous step definitions" runtime error when two step-definition methods in different classes both match the same literal step text. The achievable first version compares every catalogued `StepDefinitionAsset.pattern` against every other's, flagging exact string matches attributed to different `class_name`s — deterministic, cheap (string equality, no embeddings), and reusing only the catalog's already-recorded `pattern` field, no new asset shape. **Full Cucumber Expression/regex overlap detection (two syntactically different patterns that could still both match the same literal text) is a stretch goal, explicitly deferred** — it needs a real Cucumber Expression engine this platform has no dependency on today, and is not designed or scoped by this ADR.

### D6 — CP5's control-point discipline: deterministic gates, advisory hints, one composition rule

ADR-0040 Decision 2 requires control-point gates to evaluate only deterministic evidence, with LLM/embedding-derived assessments advisory-only, never gating. CP5's own four components do not compose uniformly against that rule, so the composition is locked explicitly rather than left implicit:

| Component | Nature | Composition |
|---|---|---|
| Orphaned-glue, primary (pattern-vs-text match, D2) | Deterministic | Contributes to CP5's own PASS/FAIL |
| Orphaned-glue, secondary (semantic hint, D2) | Advisory | Review-trigger only, never gates |
| Cross-suite near-dup sweep (D3) | Advisory | Review-trigger only, never gates — same discipline as the reuse engine's own confidence-based escalation (ADR-0044 D4(a)) |
| Promotion-wrapping reject (D4) | Composed | A deterministic-check failure (orphan-by-pattern, exact glue collision, compile failure) may gate CP5 directly; a near-dup-only finding routes to review (D4) without by itself flipping CP5's verdict |
| Aggregate cohesion — compiles, exact ambiguous-glue (D5) | Deterministic | Contributes to CP5's own PASS/FAIL |

**CP5's own PASS/FAIL verdict is driven only by its deterministic components** — compiles, exact pattern-vs-text orphan detection, exact ambiguous-glue collision. The embeddings-backed near-dup sweep, and any secondary semantic orphan hint, never by themselves fail CP5; they produce findings that join the one shared human review queue (D4), exactly as the reuse engine's own confidence-based escalation already does one layer down. This is the same shape ADR-0040 Decision 2 already required of CP2's LLM-judged checks (advisory, never gating) and the same discipline ADR-0016/ADR-0017 already established for CP1 — CP5 is another instance of this platform's deterministic-gate principle, not an exception to it.

### D7 — What CP5 reuses, and is prohibited from rebuilding

CP5 is built on top of machinery Layers 3/4's own prior ADRs already froze; this Decision locks that CP5 **reuses** each, and does not duplicate any of them:

- **The catalog** (`automation_engineering/catalog/scanner.py::reconcile`, ADR-0044 D3) — CP5's every component reads the same reconciled catalog, no second scanner.
- **The reuse engine's semantic matching boundary** (`EmbeddingProvider`, ADR-0044 D3's embeddings lean) — D3's near-dup sweep reuses the embedding call boundary, promoting `_cosine_similarity`/`_embedding_text` to shared code rather than reimplementing either.
- **The Gherkin-needs derivation** (`automation_engineering/stage/gherkin_needs.py`, built for Layer 3's stage 15) — D2's orphan check reuses `derive_feature_step_needs`/`derive_unique_step_needs` unchanged, pointed at the whole tracked feature corpus rather than one run's new features (new wiring, unchanged functions).
- **The per-asset promotion mechanism and its review model** (ADR-0045 D2/D3/D5) — D4 wraps `evaluate_promotion`/`apply_promotion`/`stage_promoted_assets` and the one shared review queue, never re-implements or re-litigates any of them.

**No new duplicate-detection mechanism, no second semantic matcher, no second review queue, and no second catalog scanner are ever built for CP5** — restated as binding (Recommendations, below), the same "no second mechanism" discipline ADR-0045 Recommendation 3 already locked for promotion's own duplicate check.

### D8 — CP7 and CP8: named, scoped, not designed here

CP7 (suite-wide quality/Sonar governance) and CP8 (static execution-readiness governance) are the deck's real content, correctly renumbered per D1. This ADR locks their **existence, scope boundary, and one inherited constraint each** — it does not design either in the detail D2–D6 gave CP5; that is a future task's own design-then-freeze work, mirroring how this ADR itself proceeded from a design proposal to a freeze.

**CP7 — scope: whole-suite Sonar/code-quality governance, distinct from CP3's per-run gate.** The LLD review's own S1 finding is confirmed and restated as binding: CP7 governs what the *entire accumulated suite* has become; CP3 (ADR-0044 D5) gates what one run's own generated Java produced. Without this distinction CP7 is a redundant CP3 re-run. **CP7 must inherit CP3's own honest Sonar story, not restart it** (LLD review's own CP3/CP4-honesty inheritance section): Sonar performs generic-quality analysis only; this platform's own architectural rules are static checks specifically because Sonar's rule engine cannot express them (the `customqa:*` arc, ADR-0044 D5's own revisions); and CP7's security dimension must be scoped down honestly (LLD review's own S3 finding) — Sonar's security ratings/hotspots are largely inapplicable to test-automation code and must not gate meaningfully on a signal that doesn't mean much for it. **Sonar Community Edition's actual claimed capabilities (security hotspots, quality-gate specifics) must be verified against the real server before CP7 is designed in detail** (LLD review's own S6 finding) — flagged as a to-verify-before-designing item, not resolved here.

**CP8 — scope: static execution-readiness governance only.** Assets present, dependencies resolvable, build/framework configuration (`pom.xml`, Cucumber, Selenium, environment config) valid and well-formed — the same static-source-only posture CP4 already established (ADR-0044 D6), no running-browser or SUT dependency. The deck's own dynamic readiness content (build succeeds, smoke test passes) is explicitly excluded from CP8 and from Layer 4 entirely (D1) — it is Layer 5's.

Neither CP7 nor CP8's detailed rule catalogue, report shape, or task breakdown is designed by this ADR. Both are recorded as deferred (Consequences, below), the same "named, scoped, detail deferred" treatment ADR-0040 Decision 1 itself gave CP2/CP3's own rule catalogues before ADR-0043/ADR-0044 later specified them.

**Amendment note (additive, 2026-08-06, ADR-0047).** ADR-0047 (Layer 4, CP7/CP8 Freeze) specifies both control points in the same detail D2–D6 above already gave CP5, resolving this Decision's own "to-verify-before-designing" precondition first: Sonar Community Edition's real capabilities were confirmed live against this platform's own server (edition genuinely `community`; the built-in quality gate is leak-period-scoped, not whole-suite; absolute measures are readable by the pipeline's own token; security-hotspot detection is real, only the review workflow is permission-gated; coverage/duplication are unmeasured, pending a JaCoCo-wiring prerequisite). CP7 ships report-only across every metric family until its own compile-state and JaCoCo triggers close; CP8 ships as a real, gating deterministic check from the start, distinct from CP5's own aggregate-cohesion compile check (D5, above). This Decision's own text is unchanged — ADR-0047 specifies it, the same relationship this ADR itself already has with ADR-0040 Decision 3's own CP5 list. See ADR-0047 for the full decision.

### D9 — Governance reporting is Layer 4's; the dashboard is Layer 7's

Layer 4 produces a governance report set — CP5, CP7, and CP8 validation reports plus a consolidated summary — consumed by Layer 5 (execution handoff) and Layer 7 (dashboard consumption). Layer 4 does **not** render a dashboard; the deck's own slide-13 Governance Dashboard content is Layer 7's job (ADR-0031), per the LLD review's own S4 finding, restated here as binding and dropped from Layer 4's own scope permanently.

### D10 — The CAP-080 "Quality Governance" name collision is disambiguated, not merged

`docs/proposals/quality-governance-framework.md` (ADR-0017, CAP-080) is an **already-live, already-wired** subsystem also named "Quality Governance," sitting immediately after CP1 in the Requirement Intelligence pipeline (Layer 1), rendering the release decision from `GroundingResult`/`ValidationResult`/`CP1Result`. It has no functional relationship to this ADR's Layer 4 — different layer, different inputs, different control points, different governing ADR. The LLD review's own Finding 0a is confirmed: this is a **naming collision only**, not a scope overlap, and it is recorded here so a future reader does not conflate the two. **No rename is authorized by this ADR** — CAP-080's frozen code and governing ADR-0017 are untouched. A future Layer 4 implementation task should refer to this ADR's own subsystem as "Layer 4 Quality Governance" or "Suite Quality Governance" (ADR-0031's own name) in any context where the CAP-080 subsystem is also in scope, to keep the two distinguishable in prose.

## Consequences

- Layer 4's CP5 is fully locked (D1–D7): the control-point numbering (D1), all four suite-integration components (D2–D5), the deterministic/advisory composition rule (D6), and the explicit reuse-not-rebuild constraint (D7).
- **CP7 and CP8 are named and scoped, not designed.** Their detailed rule catalogues, report shapes, and task breakdowns are deferred to a future design-then-freeze task, mirroring this ADR's own two-step process (design proposal, then freeze).
- **What Layer 4 does not own:** CP6 or any of Layer 5's execution/tag-selection/live-DOM-validation concerns (ADR-0044 D6, D1 above); Layer 7's dashboard consolidation (D9); CAP-080's own subsystem or its ADR-0017 governance (D10); ADR-0045's promotable gate or review model, which CP5 wraps but does not redecide (D4, D7).
- **Additive amendment notes, all recorded alongside this ADR:** ADR-0040 (an additive note near Decision 3 recording that its suite-level integration governance list is now fully specified as CP5 by this ADR); ADR-0045 (an additive note near D1 recording that CP5, now designed, is the wrapping governance D1 anticipated); ADR-0044 (an additive note near its Consequences/Ownership CP5/CP6 references confirming this ADR is where CP5 is specified in full).
- **Open TBDs this ADR does not resolve, each with a stated trigger:**
  - The orphan-detection pattern-vs-text evaluator (D2) — new build work, does not exist today; resolve at implementation.
  - The near-duplicate cluster threshold (D3) — locked as a configurable default (`0.90`), not a proven constant; resolve/tune against real observed near-duplicate pairs once the catalog has some.
  - `_cosine_similarity`/`_embedding_text`'s promotion to a shared location (D3) — a locked requirement, not yet executed; resolve at implementation.
  - Full Cucumber Expression/regex overlap ambiguous-glue detection (D5) — explicitly deferred beyond the exact-collision v1; resolve when a future task decides the v1 gap is worth closing.
  - CP7's detailed design (D8) — including Sonar Community Edition's actual verified capabilities (S6) — deferred to a future design-then-freeze task.
  - CP8's detailed design (D8) — deferred to the same future task.
  - CP7/CP8's own effort estimates — not costed by this ADR or by the LLD's own 18 PD figure, which covers the deck's mislabeled content only, not this ADR's corrected scope.

## Recommendations (permanent)

1. **No future Layer 4 implementation renumbers CP1–CP6** — CP7/CP8 are the only new numbers this ADR authorizes (D1). Reassigning CP5 or CP6 requires amending ADR-0040/ADR-0044 explicitly, not a silent Layer 4 implementation choice.
2. **No orphan or near-duplicate finding is ever auto-acted on** — flag-for-review is the only locked action for both (D2, D3). A future implementation that auto-deletes orphaned glue or auto-merges a near-duplicate cluster violates this ADR's central decision.
3. **No second human-review queue is ever opened for a CP5 finding** — a suite-level rejection routes to the same shared queue ADR-0045 D3 already established (D4). This restates ADR-0045's own Recommendation 2, extended to CP5 explicitly.
4. **No LLM- or embedding-derived signal is ever wired into CP5's own PASS/FAIL path** — the near-dup sweep and any semantic orphan hint are advisory only, always (D6; ADR-0040 Decision 2, restated as binding on Layer 4 specifically).
5. **CP5 never acquires a running-browser or SUT dependency** — compiling is Layer 4's; running is Layer 5's, permanently, not provisionally (D5, mirroring ADR-0044 Recommendation 5's own CP4 boundary).
6. **No second catalog scanner, semantic matcher, or duplicate-detection mechanism is ever built for CP5** — D7's reuse list is exhaustive; a future implementation adding a parallel mechanism for content D7 already names violates this ADR.
7. **CP7's Sonar use must extend CP3's own honest profile/scope story, never restart it** — generic-quality-only, static checks for what Sonar cannot express, and an honestly-scoped-down security dimension (D8).
