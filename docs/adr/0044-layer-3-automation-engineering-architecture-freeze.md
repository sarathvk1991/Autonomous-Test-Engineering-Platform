## Problem

ADR-0031 names Layer 3 (Automation Engineering) and its Purpose — "Generates page objects, step definitions, and test data from Layer 2's features" — but, consistent with the same deferral pattern ADR-0034 §D5 established for Layer 2 ("Layer 2's architecture-freeze ADR... with Layer 2's own designers as the deciding voice") and ADR-0043 then filled, leaves Layer 3's own design entirely to a future architecture-freeze ADR. This document is that ADR.

The committed Layer 3 LLD (`docs/proposals/layer-3-automation-engineering-lld.md`, transcribed 2026-07-29, from a 26-slide deck authored outside this repository) is evidentiary input toward that design, not itself approved — several of its components and one full section are already superseded, per its own Reviewer's note, by decisions this repository made since the deck was authored: its "Test Generator" component emits exactly the JUnit-4 runner shape ADR-0041 D3 prohibits by name; its implementation task breakdown (§23) is Layer 2's own task list, reused wholesale rather than authored for this layer; and its CP5/CP6 references (§18, §21, §22) name control points this layer does not own. Four genuine architecture questions survive that review, plus one design model the LLD's own Reviewer's note already flags as the layer's single highest-consequence decision: the reuse-safety model governing when a semantic "this step reuses that code" binding may actually be trusted. A wrong trust decision there is uniquely dangerous among everything this platform gates on, because — unlike a lint violation, a coverage gap, or a broken locator — a wrong reuse binding produces a test that runs green while testing the wrong behavior, undetectable by any deterministic check downstream of the binding itself. This ADR resolves all four questions and the reuse-safety model, and additionally resolves the LLD's own open SonarQube/CP3 question (its Reviewer's note item S4), reconciling it against ADR-0040 Decision 1's own prior, brief assignment of SonarQube-on-generated-Java to CP3.

## Decision

### D1 — Input, output, and scope boundary

Layer 3 consumes the Validated Feature Package (ADR-0043's Layer 2 output): lint-clean, tagged `.feature` files; the CP2 result; the test-data specification (ADR-0043 D7); and the derived `traceability.json` index (ADR-0043 D2). It produces the Validated Automation Package: step definitions, page objects, utility classes, Java test-data classes (D7, below), an automation coverage report, a CP3 validation report, and a CP4 validation report — for Layer 4 (Suite Quality Governance, ADR-0040 Decision 3) and Layer 5 (Test Execution) to consume.

**Layer 3's scope ends at CP3/CP4 and the Validated Automation Package hand-off.** It does not define CP5 or CP6 — those are Layer 4's suite-level integration governance (ADR-0040 Decision 3) and Layer 5's execution concern, respectively. The LLD's own slides 18, 21, and 22 name CP5/CP6 as this layer's immediate downstream consumer; per the LLD's Reviewer's note (item S7), this is out of scope for Layer 3's own freeze — restated here as this ADR's own binding decision, the same restatement pattern ADR-0043 D1 already used for ADR-0034 Recommendation 1.

### D2 — No Test Generator (Q1, S1)

Layer 3 does **not** generate test or runner classes. ADR-0041 D3 locks the suite runner model to JUnit Platform Suite (`@Suite` + `@IncludeEngines("cucumber")` + `@SelectClasspathResource`), with glue/tag/plugin configuration living in `junit-platform.properties`, not in annotations — and explicitly prohibits `@RunWith(Cucumber.class)` and `@CucumberOptions` "anywhere in this platform's generated or hand-written Java" (ADR-0041 D3, Recommendation 1). The tracked `test-suite-baseline/RunCucumberTest.java` (`@Suite` + `@IncludeEngines`, committed at `2195fbd`, per ADR-0037's resolution note) already executes every feature under that model; a per-feature runner class is not merely redundant, it is precisely the JUnit-4 shape ADR-0041 forbids by name.

The LLD's "Test Generator" component (§6, §12) emits exactly the prohibited shape — `@RunWith(Cucumber.class) public class LoginTest {}` (LLD §12, transcribed verbatim). Per the LLD's own Reviewer's note (item S1), this component is **formally deleted** as a code generator, not merely reworked: Layer 3 generates step definitions, page objects, and utilities (D3–D4, below) and test-data classes (D7, below); it does not generate any class whose purpose is to select or run features. Which features a given run executes is a Layer 5 configuration concern — tag/property-driven selection at execution time via `junit-platform.properties` overrides, not baked into a generated class.

This binds the LLD's §6 component table and §20 Work Product table wherever they name "Test Generator"/"Automation Scripts" as a Layer 3 output: no such artifact is produced. The LLD's own §26 effort estimate (28 PD) includes "Test Generator 3 PD," which this deletion removes — the real Layer 3 effort is lower than the LLD's own headline figure.

### D3 — Reuse-first via a semantic asset catalog (Model B) (Q2)

The LLD's own stated differentiator (§5, "Reuse First, Generate Later": Search Existing Assets → Reuse → Generate Only Missing Assets) is locked as Layer 3's core generation discipline: generation happens only for an asset with no acceptable reuse match.

**Catalog model — Model B, a persistent store.** The asset catalog persists across runs; a per-run catalog cannot accumulate reuse, since reuse is a cross-run property by definition (a step definition generated in run N is only "reusable" if run N+1 can find it). At the start of each run, the catalog is **reconciled** against a scan of the tracked baseline's committed Java — not rebuilt from scratch, and not trusted unconditionally from its own prior state either — so the actual committed code remains the effective source of truth the catalog describes, not a stale index of what the code used to contain. The catalog's exact storage location relative to the tracked baseline (`test-suite-baseline/`) and the untracked per-run workspace (ADR-0037) is **TBD**, resolved at implementation (Consequences, below) — this ADR locks that the store is persistent and separate from both, reconciled against the tracked baseline at run start, not that it lives at any specific path.

**Matching strategy — semantic, not exact-string.** Reuse discovery matches a Gherkin step's *meaning* against the catalog's own recorded intent (LLD §7's `supportedActions` field: `["login", "logout", "authentication"]` for `LoginSteps`, not a literal string list) — "When user logs in" matching `LoginSteps` (LLD §8) is a semantic match, not a substring match. This is the LLD's own stated differentiator (§5) from "generic AI test generation solutions," and the only reading consistent with §7's `supportedActions` shape, §8's free-text step input, and §19's "reuse confidence low" human-review trigger — none of which are meaningful concepts for exact-string matching, which either matches or it doesn't and has no "confidence" to be low.

**Semantic matching mechanism — TBD, embeddings favored.** Whether the MATCH step (catalog lookup) is performed via embeddings or a per-step LLM call is left to implementation. Embeddings are cheaper, batchable across a run's full step set, and cacheable across runs (the catalog itself is persistent, above); a per-step LLM call would multiply Layer 3's own model-call volume by roughly the step count of the entire corpus, on top of whatever calls generation requires — exactly the free-tier request-volume pressure the Layer 2 live measurement already exposed (a real `429 RESOURCE_EXHAUSTED` failure at the free tier's 15-requests/minute quota, mid-run — `DEMO_RUNBOOK.md` Stage 17). This ADR records a lean toward embeddings for MATCH, reserving LLM calls for GENERATING genuinely-missing assets, as a TBD-with-lean, not a lock — the exact mechanism is deferred to implementation (Consequences, below).

### D4 — The reuse-safety model (Q2-safety) — the critical decision

This is the single decision in this ADR most load-bearing for the whole layer's trustworthiness, and it is stated here at full length rather than compressed, because compressing it is exactly the failure mode it exists to prevent.

A semantic reuse binding — "this Gherkin step reuses that catalogued step definition" — is trusted only when **all three** of the following hold. Any one failing routes to human review, never to a silent fallback:

(a) **Match confidence ≥ a set threshold.** Below threshold, **escalate to human review** — the LLD's own condition (§19, "Reuse confidence low" as a Human-in-the-Loop trigger), locked here as binding rather than advisory-only prose.

(b) **Content-hash validation that the catalogued code is current.** The catalog (D3) is reconciled at run start, but reconciliation and validation are not the same guarantee — (b) is the check that the *specific* asset a match is about to bind to has not drifted from what the catalog's entry describes since it was last indexed. This catches catalog staleness specifically, a failure mode (a) and (c) do not cover.

(c) **Signature/parameter fit between the step definition and the Gherkin step it is bound to.** A step definition whose intent plausibly matches but whose parameter shape does not (wrong arity, wrong type, a missing capture group) is a gross mis-binding — this check catches it structurally, before the binding is ever trusted, rather than relying on (a)'s confidence score alone to have caught it semantically.

**Rationale, stated plainly, because it is the reason all three are required and not just one:** a wrong semantic binding produces a test that runs **green while testing the wrong behavior**. It compiles. It runs. It passes. It is invisible to every deterministic downstream gate this platform has — CP3's coverage counts (the step is "covered," just by the wrong code), CP4's locator health (irrelevant to which step definition ran), SonarQube's code quality (the bound code may be perfectly clean; wrong-target reuse is not a code-smell). This is the one Layer 3 failure mode nothing downstream detects. Content-hash (b) catches staleness; signature-fit (c) catches gross structural errors; the confidence gate plus human-in-the-loop (a) catches the remaining, hardest case — a match that is neither stale nor structurally mismatched, merely plausible-but-wrong. No one of the three subsumes the other two; each closes a distinct gap the others leave open.

**This mirrors ADR-0040 Decision 2's deterministic/advisory discipline directly**, applied one level deeper than a control-point gate itself: the semantic match (a similarity score, however computed) is exactly the kind of AI-judged signal Decision 2 already requires be advisory only, never itself the gate. Here, the semantic match is advisory **until** the two deterministic checks — content-hash (b) and signature-fit (c) — verify it structurally; only a match that clears the confidence threshold **and** passes both deterministic checks is ever trusted as a binding. A match that clears confidence but fails either deterministic check is not silently accepted at reduced confidence — it escalates, the same outcome as failing (a) outright.

**Clarification note (additive, 2026-07-30).** This text states check (c) as "signature/parameter fit between the step definition and the Gherkin step it is bound to" and exemplifies it only on step definitions. Layer 3's reuse engine implementation (`automation_engineering/reuse/engine.py`) found that D3's own catalog and reuse-first discipline are asset-type-agnostic — the catalog records step definitions, page objects, AND utilities alike (D3 above; `automation_engineering/catalog/models.py`), and this Decision's own rationale paragraph ("a wrong semantic binding produces a test that runs green while testing the wrong behavior... invisible to every deterministic downstream gate") names no asset type — a step definition wrongly bound to a page object lacking the method it needs produces the identical failure signature. Check (c) is accordingly read here as generalizing to **structural fit**, with two realizations, neither of which edits this Decision's own text or weakens "all three, every time":
- **Step definitions — SIGNATURE-FIT, unchanged.** Fully decision-time and precise: a Gherkin step's own captures (count, order, type) completely determine the parameter shape a bound step definition must have, and the catalog already records the exact correlation to compare against (D3's `signature_alignment`). Nothing about this realization changes.
- **Page objects / utilities — METHOD-FIT, split across two moments, honestly.** At reuse-decision time, the engine can only run a **coarse class-compatibility screen**: does the catalogued class provide *some* method whose parameter shape (arity, per-position type) could accept the call — escalating only on gross incompatibility (e.g. a step needing an argument matched to a class with only zero-arg methods). This screen structurally **cannot** detect a class that has some shape-compatible method but not the *specific* one the binding actually needs (e.g. a `LoginPage` reused for a step needing `clickForgotPasswordLink()`, where `LoginPage` merely happens to have some other zero-arg method) — which specific method a not-yet-written step definition will call is not knowable until a future generator actually writes that call. **The precise check is therefore the generator's own obligation, not this engine's**: before binding a step to a reused page-object/utility method, the generator that eventually implements Layer 3's generation step must verify the specific method it is about to call is actually present, and escalate/regenerate if it is not. The reuse engine's `TrustedReuse` outcome carries the full method inventory (names included) precisely so that future check has what it needs; it does not perform that check itself. The gap D4 exists to close is therefore fully closed for page objects/utilities only once **both** halves exist — the coarse screen (built) and the generator's precise check (a tracked obligation on the future generator task, not yet built) — and this note records that split explicitly rather than letting the coarse screen alone be mistaken for the whole of (c).

**Precise method-fit DISCHARGED for page objects (additive, 2026-07-31, the Layer 3 page-object generator build).** The obligation the paragraph above tracked — "a tracked obligation on the future generator task, not yet built" — is now built, for page objects specifically (utilities remain that build's own, still-open, honestly-carried-forward scope). `automation_engineering/generation/method_fit.py`'s `verify_specific_method_fit` performs the PRECISE check: given a `TrustedReuse` (the coarse screen already passed) and the specific method name a step-def call site is about to use (caller-supplied, per this note's own "not knowable until a future generator actually writes that call"), it checks that name against `TrustedReuse.asset.methods` — the exact inventory this note said would be handed over for exactly this purpose — and returns an `Escalation` (reusing `EscalationCheck.METHOD_FIT`, the SAME check identity the coarse screen itself uses, since this is check (c) closing its own gap, not a fourth check) when the name is absent or its shape does not fit. Wired into `automation_engineering/generation/orchestrator.py`'s own NO_MATCH branch — the ACTUAL binding point this note named — via an optional `page_object_request` parameter: supplied, a step is generated against a page-object binding only once BOTH halves of (c) verify clean; a specific-method failure escalates the WHOLE step, never a silent fallback. Proven directly against this note's own illustrative example (a `LoginPage` with only `open()`, reused for a step needing `clickForgotPasswordLink()`): the reuse engine itself returns `TrustedReuse` (the coarse screen genuinely passes, not a contrived case), and the precise check still escalates — `tests/unit/test_automation_engineering_generation_page_object_orchestrator.py::TestPreciseMethodFitEscalatesTheInsufficientCase`. Check (c) is now fully closed for page objects: coarse (decision-time) **and** precise (generation-time), both built, neither mistaken for the whole of (c) alone. Utilities are unaffected by this note — `verify_specific_method_fit` is written against the same `PageObjectAsset | UtilityAsset` union the coarse screen already uses (so a future utilities task does not need to re-derive this logic), but no orchestration built here ever calls it with a `UtilityAsset`; that remains the next task's own obligation to discharge, carried forward the same honest way this one was.

**Precise method-fit DISCHARGED for utilities too — investigated, not assumed (additive, 2026-07-31, the Layer 3 utilities generator build).** The paragraph above deferred utilities as "that remains the next task's own obligation to discharge" without establishing that the obligation is actually load-bearing for utilities specifically — this build investigated that question directly rather than inheriting "identical treatment" as a foregone conclusion. Finding: utilities carry the SAME precise-method-fit risk page objects do, and the ONE real utility class this platform has ever committed makes the risk sharper, not weaker — `test-suite-baseline/src/test/java/com/automation/base/ConfigReader.java`'s two public methods, `env(String)` and `data(String)`, are semantically distinct (SUT-binding vs. test-data, ADR-0037 D3's own boundary) yet share an IDENTICAL parameter shape (`String -> String`). A coarse arity/type screen cannot distinguish them AT ALL: a step needing `ConfigReader.data("username")` reused against a candidate whose only relevantly-shaped method is `env` clears the coarse screen (`_check_method_fit`) cleanly and would bind to the wrong accessor. `automation_engineering/generation/method_fit.py`'s `verify_specific_method_fit` is REUSED UNCHANGED (it was already written generically over `PageObjectAsset | UtilityAsset` for exactly this reason) — no new discharge logic exists; only the orchestration around it (`automation_engineering/generation/utility_orchestrator.py`, mirroring `page_object_orchestrator.py`'s own wiring exactly) and a second optional parameter, `utility_request`, on `automation_engineering/generation/orchestrator.py`'s own NO_MATCH branch, alongside `page_object_request`. Proven directly against the `env`/`data` scenario this note's own investigation identified: the reuse engine itself returns `TrustedReuse` (coarse genuinely passes), the precise check still escalates, the utility generation seam is never called — `tests/unit/test_automation_engineering_generation_utility_orchestrator.py::TestPreciseMethodFitEscalatesTheInsufficientCase`. Check (c) is now fully closed for utilities too: coarse **and** precise, both built. **There is no fourth, still-deferred catalog asset kind left** — step definitions, page objects, and utilities (D3's own three) are all now legitimately handled by a generator.

**`NO_MATCH`/generate was bootstrap-only — found and resolved, a `generate_floor` tier added below check (a) (additive, 2026-08-05, a live re-run against the free tier).** D3's own "Reuse First, Generate Later" states generation is for "an asset with no acceptable reuse match" — not, as the implementation until this note actually behaved, only for a need the matcher could not compare against anything at all. A live run (`output/executions/run-20260805T105026014856Z-987575c0/automation_engineering_report.md`) matched 49 real Gherkin step-needs against the tracked baseline's real, non-empty 2-asset catalog and found every one escalated on confidence (D4(a)) — zero generated, zero bound. Root cause: `LiveSemanticMatcher.match` (`automation_engineering/reuse/live_matcher.py`) returns one `MatchCandidate` per catalog asset unconditionally (its only empty-result path is an empty catalog); `decide_reuse` only ever produced `NoMatch` when `match` returned nothing at all. Once a catalog has been populated even once — the normal state for every run after the first — `NoMatch`/generate was therefore **unreachable**: a need matching nothing relevant in the catalog escalated to human review instead of generating, contradicting this Decision's own discipline.

**Resolved**: a third tier, `DEFAULT_GENERATE_FLOOR = 0.70` (`automation_engineering/reuse/engine.py`), sits strictly below `DEFAULT_CONFIDENCE_THRESHOLD` (D4(a)'s own 0.75). `decide_reuse` now reads `best.confidence < generate_floor` as `NoMatch` — not even plausible, the same outcome an empty catalog already produces, for the same reason (nothing worth a human's review time) — before D4(a)'s own confidence check ever runs. `generate_floor <= best.confidence < confidence_threshold` still escalates exactly as D4(a) always specified; `best.confidence >= confidence_threshold` still runs D4's full three-check safety (content-hash (b), structural fit (c)) completely unchanged. This is additive to D4, not a revision of it: the three-check safety this Decision states at length is untouched — the new tier sits strictly below check (a)'s own floor and only ever reroutes candidates that were never plausible in the first place, so it cannot mask a should-have-been-trusted or should-have-escalated case (the danger direction D4 exists to prevent — a wrong, confident bind — is still gated by all three checks, exactly as before).

**The floor is calibrated from real score data, not guessed**, per this Decision's own "TBD, embeddings favored" (D3) now having real embedding-similarity numbers to calibrate against, deferred at D3's own writing to "whenever a `GOOGLE_API_KEY` is actually available to test against" (`.reuse/live_matcher.py`'s own docstring) — now available. The live run's own 49-need band across genuinely-unrelated SauceDemo steps landed in `[0.5707, 0.6688]`; a fresh live probe (same catalog, same embedding model) against two more deliberately-novel, unrelated needs landed in `[0.5196, 0.5696]`, confirming the band rather than contradicting it — short, unrelated technical text has a HIGH embedding-similarity floor with this model family, never near zero. The SAME catalog's own exact-text match scored 0.9843, and a full paraphrase of it scored 0.8980. These two observed bands — "nothing relevant" topping out at 0.6688, "genuinely relevant" starting at 0.8980 — do not overlap; a simple global floor cleanly separates them without needing a relative-gap or score-normalization criterion, and 0.70 sits at their approximate midpoint, comfortably clear of both. Proven directly that the fix actually fires on real data, not merely that a floor exists: `tests/unit/test_automation_engineering_reuse_engine.py::test_below_floor_similarity_is_no_match_not_escalation_with_a_non_empty_catalog` reproduces the live run's own below-floor case against a non-empty catalog and gets `NoMatch`, where the pre-fix engine would have escalated every time.

**Six pre-existing unit tests encoded the old, two-tier assumption directly** (a stub confidence such as `0.1` or `0.5` standing for "any confidence below threshold escalates," true before this note and false now for confidence that low) and were updated to a confidence inside the new escalate band (`0.72`) so each test continues proving what it always intended — confidence-based escalation surfacing — rather than being incidentally broken by the calibration; no test's assertions or structure changed, only the fixture confidence value. `generate_floor` is independently configurable, mirroring `confidence_threshold`'s own pre-existing configurability. Verified: `make test` 5387 → 5390 (+3, all in `test_automation_engineering_reuse_engine.py`); `make lint` clean; mypy (informational) 432 → 432, no rise. **Finding 2 (from the same live run), RESOLVED (additive, 2026-08-05, a follow-up task).** Generation calls (`LiveFeatureContentGenerator`/`LiveFeatureRemediator` and Layer 3's own `live_*_generator.py` peers) made exactly one call with no retry — unlike the embedding boundary's own pacing/retry (this same note's FIX 3) — so a `429` on a generation call failed that one need outright (isolated to it alone, never the whole stage, but not retried). Resolved at the ONE shared call site all six of those callers route through — `requirement_intelligence/llm/providers/gemini_provider.py::GeminiProvider._execute`, outside this ADR's own Layer 3 scope but the correct single point of fix — which gained the identical pacing/bounded-retry-with-backoff shape mirrored (not code-shared; see that module's own docstring for why) from this note's own embedding-boundary fix. No change was needed to any of the six generation call sites themselves. See `docs/architecture/architecture-baseline-v2.md` item 24 for the full account of both findings.

### D5 — CP3: coverage-gated, reuse-reported, SonarQube-hard-gated (Q4)

CP3 gates deterministically (ADR-0040 Decision 2) on always-meaningful static criteria, computed from the generated Java and feature files alone, no live infrastructure required for this part: step coverage = 100%, scenario coverage = 100%, zero unmapped steps, zero duplicate steps.

**Reuse % is reported, never gated.** An empty catalog's bootstrap run reuses 0% of its steps — correctly, not as a failure — since there is nothing yet to reuse; gating CP3 on a reuse threshold would fail every platform's first Layer 3 run by construction, before the catalog (D3) has had a single run to populate itself from. This mirrors the same discipline CP2's own criteria already apply (ADR-0043 D5, ADR-0040 Decision 2): every CP2 rule is an exact, always-meaningful floor (0 lint violations, 100% acceptance-criteria coverage, tag presence, 0 duplicates) — never a soft percentage threshold like the Layer 2 LLD's own, since-superseded "Naming Compliance >95%"/"Tagging Compliance >95%" criteria (`docs/proposals/layer-2-feature-engineering-lld.md` §15). The Layer 3 LLD's own §15 rule table names Reuse Percentage ">70%" as a Pass Criterion alongside coverage/duplicate criteria, undifferentiated; this ADR corrects that — reuse moves to CP3's report, not its gate, alongside the criteria (feature/scenario/step coverage, duplicate/unmapped steps) that stay exactly as gates.

**SonarQube's quality gate is a hard CP3 requirement — locked, not deferred.** ADR-0040 Decision 1's own table already assigns "SonarQube on generated Java, using the `customqa:*` quality profile (ADR-0037)" to L3/CP3; this ADR specifies what that assignment means operationally and confirms it as this layer's own binding decision: **CP3 does not pass unless a running SonarQube server scans the generated Java and its quality gate — evaluated against the `customqa:*` profile — passes.** This resolves the LLD's own open question (its Reviewer's note item S4): the LLD's §15 CP3 rule table names only coverage/reuse/duplicate criteria, and §18 treats SonarQube as a separate step "bridging into CP5" — read literally, the LLD would place Sonar outside CP3 entirely, in tension with ADR-0040 Decision 1's own table. ADR-0040 wins: it is the Accepted, more specific control-point ADR, while the LLD is Submitted, under review; and per the LLD's own Reviewer's note item S7, CP5 is out of Layer 3's scope in the first place, so "bridging into CP5" cannot be where SonarQube's gate actually lives. SonarQube is folded into CP3 itself, exactly as ADR-0040 Decision 1 already named.

**A related tension, reconciled here rather than silently left standing.** ADR-0037 itself describes the `customqa:*` profile as "a Layer 4 (Suite Quality Governance) asset: it is the rule set Layer 4 evaluates generated code against" (ADR-0037, "Two-tier split, locked"). ADR-0040 Decision 1 — Accepted after ADR-0037, and never listed as amending it — nonetheless assigns the profile's *evaluation* to CP3/Layer 3. **Where this prompt's framing and an Accepted ADR's own prior text disagree, the later, more specific Accepted ADR wins**, and that is the resolution here: these two statements are reconcilable, not actually contradictory, once separated into two distinct claims. **Where the profile lives and is versioned** (the tracked baseline, ADR-0037's "versioned alongside the tracked baseline it governs," Recommendation 3 — unchanged, still true) is a different question from **which layer evaluates generated code against it** (Layer 3's own CP3, ADR-0040 Decision 1 — the assignment this ADR now specifies in full). ADR-0037's "Layer 4 asset" phrasing describes the profile's *origin and stewardship*, not its *evaluator*; ADR-0040 Decision 1 is the later, more specific, Accepted statement of who gates on it, and wins on that specific question. Neither ADR's Decision text is amended by this observation; it is recorded here because a reader moving from ADR-0037 to ADR-0040 to this ADR would otherwise trip on the apparent conflict.

**Infrastructure consequence, stated plainly, not left implicit.** Layer 3 hard-requires a running SonarQube server, reachable, in every environment it runs or is tested against — production, CI, and any local/demo environment claiming to exercise CP3 end-to-end. This is the one control-point gate in the platform with a live-infrastructure dependency; ADR-0041's own Consequences already named "CP3's SonarQube scan of generated Java" among the platform's new runtime prerequisites, alongside JDK 21 and Maven. This ADR does not introduce that dependency — it specifies exactly where it binds (CP3's own pass/fail, not an advisory side-report) and states it explicitly so it is a known operational requirement, never a surprise discovered when a demo or a CI run has no Sonar server to reach.

**`customqa:*` plays a dual role, both recorded here.** The same rule set CP3 evaluates against is also fed into Layer 3's own step-definition and page-object generation prompts, as generation constraints — the same discipline ADR-0041's Consequences already establish for its own D3/D4/D5 ("Layer 3 generation constraints" that "must appear in Layer 3's generation prompts"). Code is meant to be born compliant with `customqa:*`, with the CP3 Sonar scan verifying that, not discovering violations for the first time. Stated as the operating principle: **constrain at generation, verify at the gate, so the gate rarely fires** — the same "reuse first, generate later" posture (D3) applied to quality: prevent the violation at generation time rather than relying on the gate to catch it after the fact.

**Gap note, load-bearing (additive, 2026-08-04, Layer 1-3 end-to-end integration run).** The "born compliant, verified compliant" story two paragraphs above (constrain at generation, verify at the gate) is currently INCOMPLETE, verified directly against a live SonarQube server (26.4.0.121862) and this repository: the `customqa:*` profile this Decision names as CP3's evaluation target has never been created as an artifact anywhere (repository-wide search for a profile export/XML finds none — only prose and rule-id strings in a fixture file) and has never been imported into any SonarQube server, live or otherwise. `Automation-POC`'s Java quality profile is the built-in `Sonar way` (549 rules), not `customqa:*`. Consequence, stated plainly: **CP3's Sonar gate, as it can be exercised today, enforces `Sonar way`, not `customqa:*`** — a real, running gate against the wrong rule set, not a broken gate. This Decision's own text (CP3 does not pass unless the quality gate "evaluated against the `customqa:*` profile" passes) is unchanged and remains the binding target; this note records that the target is unmet, not that the Decision is wrong. See ADR-0037 Recommendation 3's own amendment note (this same date) for the profile-versioning half of this gap. **Resolution trigger:** the `customqa:*` profile is authored as a real, versioned artifact (per ADR-0037 Recommendation 3) and imported into whatever SonarQube server CP3 targets, in every environment claiming to exercise CP3 end-to-end.

**Discovery addendum (additive, 2026-08-04, F4 discovery — the decision surface for making this gate real, not chosen here).** Investigated directly against the live server's own rule catalog before assuming "author the profile" is a uniform, mechanical task: it is not, because the two evidenced `customqa:*` rules are not the same kind of thing.

- **`customqa:long-method`** ("keep every generated method under 40 lines") is an EXISTING built-in rule, `java:S138` ("Methods should not have too many lines," a configurable `max` parameter, default 75). Making this half of the gate real is cheap: a quality profile activating `S138` at `max=40` (plus whatever other stock rules the profile should also carry) is a normal SonarQube profile export, versionable exactly as this ADR and ADR-0037 already describe.
- **`customqa:direct-webdriver-action`** ("never call a WebDriver method... in a step definition; every UI interaction must go through a page-object method") is NOT a single existing rule and cannot be activated as one. No Selenium/WebDriver rule and no layering/architecture rule exists in this server's Java catalog. What the server DOES support, confirmed directly (not assumed): TEMPLATE rules (`java:S2253`/`java:S3688`, "Track uses of disallowed methods/classes") that can ban `org.openqa.selenium.WebDriver`'s methods GLOBALLY, with no built-in per-package scoping — composed with a separate, also-native project setting (`sonar.issue.ignore.multicriteria`, confirmed present) to exclude that ban for paths under `com/automation/pages/**`. This composition is real and native (no custom Java analyzer plugin needed, and none was found to be supported as an extension point on this server at all) — but it enforces the rule by FILE PATH, not by verified class role, and it lives in project settings, a different artifact from quality-profile content.

**The decision this surfaces, for a future task, not resolved here:** for `direct-webdriver-action` specifically, three honest options exist — (1) the rule-plus-exclusion composition above, accepting the path-based approximation; (2) a genuine custom Sonar analyzer plugin (a separately versioned Java module; no evidence found that this server's edition even supports one, and heavyweight regardless); (3) drop it from the Sonar gate and enforce it as a static Python check inside Layer 3 itself, the same "static, no SUT dependency" posture D6/CP4 already established for locator health — arguably a MORE precise expression of "does this class call WebDriver directly," since it can inspect the actual generated file's own class name/package rather than relying on a project-level path-exclusion staying in sync with `com.automation.pages`'s naming convention. This ADR's own Decision text (CP3 gates on `customqa:*` via Sonar) is unchanged by this addendum; if option (3) is ever chosen for this specific rule, that would be a Decision-level amendment to make explicitly, not something this addendum performs.

**Decision note (additive, 2026-08-04, F4 revision — the discovery addendum above's decision surface is now resolved: Path A). This is a documentation-only note; it locks the design, it builds nothing.** The two `customqa:*` rules are verified by two different mechanisms from here on, and CP3's Sonar-hard-gate story is corrected to say so plainly, not silently narrowed.

- **`customqa:long-method` — VERIFIED BY SONARQUBE.** The existing native rule `java:S138` ("Methods should not have too many lines"), activated at `max=40` inside a `customqa:*` quality profile, versioned in the tracked baseline exactly as ADR-0037 Recommendation 3 already says — now an instruction to actually follow, not aspiration. CP3's Sonar hard gate verifies this rule directly, for real, once that profile exists on the target server (item 18/21's own tracked build task).
- **`customqa:direct-webdriver-action` — VERIFIED BY A STATIC CHECK IN LAYER 3, NOT SONAR.** Chosen over the discovery addendum's other two options (the file-path-exclusion composition, and a custom Sonar plugin) because it is an architectural constraint about a call's CALLER-CLASS-ROLE ("no WebDriver calls in a step-definition class; page objects are exactly where they belong") — SonarQube's own rule engine cannot natively express caller-role constraints, and the file-path-exclusion path only approximates it (by convention, drifts if the path changes, and lives in project settings rather than the profile ADR-0037 governs). A static check inspecting the real generated class's own package/imports directly (mirroring D6/CP4's already-established "static, no SUT dependency" posture for locator health) is not a fallback — it is the MORE PRECISE expression of this specific rule, fully in-repo, versioned with the rest of Layer 3's own code rather than server-side configuration.

**CP3's Sonar-hard-gate story, corrected.** The Decision text above ("CP3 does not pass unless a running SonarQube server scans the generated Java and its quality gate — evaluated against the `customqa:*` profile — passes") is UNCHANGED and remains binding, but its own "the `customqa:*` profile" now names the SONAR-EXPRESSIBLE SUBSET of `customqa:*` (`long-method` today; any future rule this discovery's category (1) test also clears) — never the whole rule set, since part of it was never expressible there. **CP3's own composite gate, stated in full:** CP3 passes only if BOTH the Sonar quality gate (verifying the Sonar-expressible subset) AND Layer 3's own static architectural checks (verifying `direct-webdriver-action` and any future caller-role rule) pass. Neither replaces the other; neither is downgraded to advisory — this is correct PARTITIONING of one verification obligation across the two mechanisms actually capable of each half, not a weakening of either. The earlier framing — "the CP3 Sonar scan verifying that [customqa:* compliance]," singular, all of it — is corrected here as partly aspirational: it was written assuming every `customqa:*` rule would land in one Sonar profile, before the profile, or a real scan against real code, ever existed (F4's own discovery: the FILE-mode "evidence" both rules were originally justified against was self-labeled synthetic-fixture data, never a real scan). The generation-time half is untouched by this correction: `customqa:*`'s CONSTRAINTS still appear verbatim in the generation prompts (D5's own "constrain at generation, verify at the gate" principle, above) — code is still born compliant with BOTH rules; only which mechanism verifies which rule at the gate has changed.

**Test story — the adapter is stub-tested; the live gate is exercised only where Sonar exists.** The SonarQube adapter — submitting a scan, polling for completion, parsing the quality-gate result — is unit-tested deterministically against a stub/fake, the same seam pattern already established for the LLM providers (`StubFeatureRemediator`/`FakeProvider`, ADR-0043's D5 build). Unit tests stay infrastructure-free; they never require a live Sonar server. A live SonarQube server is required only for the integration test that exercises the real gate end-to-end, run where Sonar is actually present — mirroring the same live-vs-stub split already established for `LiveFeatureContentGenerator`/`LiveFeatureRemediator` vs. their stub peers. Recorded explicitly so CP3's testability discipline is clear from the outset: "CP3 needs a live SonarQube server" must never be read as "every unit test needs a live SonarQube server."

**Third customqa:* revision (additive, 2026-08-05, the Sonar-config discovery task) — `long-method` also moves off the Sonar gate; both rules are now static.** The prior revision (immediately above, 2026-08-04) narrowed "the `customqa:*` profile" CP3's Sonar gate evaluates to "today just `long-method`" and left it there as the Sonar-expressible half. A dedicated Sonar-configuration discovery, run against this platform's actual generated-code layout rather than against the profile mechanism in isolation, found that framing was itself premature: `java:S138`'s own rule metadata is permanently `"scope":"MAIN"` (confirmed directly against the live server, and already recorded as this build's own "Open gap" in `test-suite-baseline/sonar/README.md`) — a property of the rule itself, not something a quality profile's activation can override — while every class Layer 3 generates or promotes (step definitions, page objects, utilities alike) is placed under `src/test/java` by this platform's own deliberate, ADR-0037 Path A architecture, not by accident (`automation_engineering/catalog/scanner.py`'s `JAVA_SOURCE_SUBPATH`). A `MAIN`-scope rule never evaluates `testSourceDirectory` content, on any project, on any server — `long-method`'s Sonar path was live and mechanically correct (the README's own proof: a real 47-line method flagged under a temporary `src/main` tree) and simultaneously **permanently inert against the real code it exists to check**, for a structural reason no profile edit can fix.

This discovery also investigated the one Sonar-side escape hatch that could, in principle, make `S138` reach `src/test/java`: repointing the scanner's own `sonar.sources`/`sonar.tests` configuration so the generated-code tree is classified as `MAIN`-scope source rather than test source. Rejected, not merely set aside: doing so does not selectively re-scope `S138` alone — it re-scopes **every** `MAIN`-scope rule already active in the `customqa` profile (the full `Sonar way` baseline this profile extends, `test-suite-baseline/sonar/customqa-profile.xml`) onto that tree at once, roughly 408 rules never chosen or reviewed for applicability to generated test-support code, activating en masse as an accidental side effect of a config change aimed at exactly one of them. That is a correctness hazard wearing a config tweak's clothes, not a targeted fix, and it is rejected on that basis alone — no clean, single-rule Sonar-side fix exists.

**Resolution: `long-method` is verified by a static Layer 3 check, mirroring `direct-webdriver-action` exactly.** `automation_engineering/cp3/architecture.py::evaluate_long_method` is built alongside `evaluate_direct_webdriver_action` in the same module, the same static, `javalang`-based, no-SUT/no-Sonar/no-network posture (D6/CP4's own discipline, cited throughout this Decision already). It measures a method's own line span (declaration line through closing-brace line, via `automation_engineering.catalog.java_source.declaration_line_span` -- the same start/end anchors the catalog's own `extract_declaration_span` already uses for content-hashing) against the rule's own threshold (`MAX_METHOD_LINES = 40`, the same value the now-inert `customqa-profile.xml` activates `S138` at) and flags any method whose span exceeds it -- in ANY generated class, not step-definition-scoped the way `direct-webdriver-action` is, since `long-method` is a per-method size rule with no caller-class-role restriction. Wired into `evaluate_cp3` (`automation_engineering/cp3/gate.py`) as a seventh CP3 criterion (`CRITERION_LONG_METHOD`, `CP3_CRITERIA` now seven entries), composed alongside the other six exactly as `direct-webdriver-action` already was; `overall_verdict` remains "PASS iff every named criterion is PASS."

**CP3's Sonar-hard-gate story, corrected a second time.** The 2026-08-04 revision's own framing -- "the `customqa:*` profile" naming "the Sonar-expressible subset (`long-method` today)" -- is now itself corrected: **the Sonar-expressible subset of `customqa:*` is empty.** Neither evidenced `customqa:*` rule is verified by Sonar any longer. This is not a retreat from D5's own binding text ("CP3 does not pass unless a running SonarQube server scans the generated Java and its quality gate ... passes") -- that text is unchanged and the Sonar criterion remains a hard, required CP3 gate -- but what it verifies has narrowed to **generic Java quality**: the built-in profile's own stock rules (`Sonar way`, the 549-rule baseline `customqa-profile.xml` already extends), the platform-wide quality bar every generated class should clear regardless of this platform's own two architectural rules. **CP3's own composite gate, stated in full, a third time:** CP3 passes only if the Sonar quality gate (generic Java quality) AND `direct-webdriver-action` (static) AND `long-method` (static) all pass, alongside the four coverage criteria -- seven criteria, all required, none advisory. This is not a weaker verification story than the original "SonarQube hard-gates `customqa:*`" framing -- it is the same two rules, verified by whichever of the two mechanisms can actually reach the real code, stated honestly instead of aspirationally for the second rule too.

**The `customqa` profile artifact and its live admin proof are not wasted, even though `long-method`'s own activation inside it is now superseded.** Both were real, necessary work: the profile's own creation and live import (this ADR's Consequences, and `architecture-baseline-v2.md` §4 item 21's own build-task-1 record) is what *produced* the proof that exposed this gap -- without a real profile, a real import, and a real scan against a deliberately-placed `src/main` proof file, "`S138` is `scope:MAIN` and cannot reach `src/test/java`" would have remained a theoretical rule-catalog property, not a verified, load-bearing fact about this platform's own architecture. The admin procedure also validated the Sonar mechanism itself (submit → poll → quality-gate fetch, a real server, a real token) for whatever role Sonar's quality gate keeps -- which, per the correction above, is now generic Java quality, not `customqa:*` specifically. **Disposition, decided here:** the `customqa-profile.xml` artifact and its `S138`-at-`max=40` activation are LEFT IN PLACE, unedited -- removing the activation would not change CP3's behavior (this project has no tracked `src/main` tree for `S138` to ever evaluate, live or otherwise) and the activation itself is now harmless, historically accurate evidence of the mechanism proof, not a functional part of any gate. `test-suite-baseline/sonar/README.md` is updated (this same date) to state its superseded status plainly, so a future reader of the profile artifact is not misled into thinking Sonar enforces `long-method` on this platform. The profile's OTHER role -- carrying the generic `Sonar way` baseline CP3's Sonar criterion now actually gates on -- is unaffected and continues exactly as before.

**Coverage-for-promotion semantics, decomposed per-asset (additive note, 2026-08-06, companion to ADR-0045 D2's own additive note this same date).** D5's own composite gate, above, produces ONE `Cp3Result` for the whole run -- `overall_verdict` is "PASS iff every one of the seven named criteria is PASS," and that has not changed; CP3 as a RUN-LEVEL VERDICT (does this run's own generated automation meet the bar, for reporting) is unaffected by this note. What this note resolves is a DIFFERENT question ADR-0045 D2 depends on: what CP3 evidence should gate ONE candidate's OWN promotion. Read literally, "step coverage = 100%, zero unmapped steps" (D5's own text, verbatim) is a claim about the WHOLE RUN, and a live confirming run showed that reading, applied uniformly to every promotion candidate, has a real cost: one need escalating anywhere in a batch fails the whole run's coverage criteria, and if every candidate is gated against that ONE shared verdict, an unrelated escalation blocks assets that generated perfectly cleanly.

**The reframing:** for PROMOTION-GATING purposes (never for the run-level `Cp3Result.overall_verdict`, which stays exactly as computed), the three coverage criteria (`step_coverage`, `scenario_coverage`, `unmapped_steps`) answer "of the needs that RESOLVED to an asset (`Generated*`/`Bound*` — ADR-0044 D4's own outcome vocabulary), are those mapped?" — not "did every need in the batch resolve?" An `Escalated*` need is, by construction, never a promotion candidate at all (ADR-0045 D3, unchanged) — nothing was generated for it to promote, so it has no OWN entry in the coverage family a candidate's own gate could meaningfully check. A candidate that IS a `Generated*`/`Bound*` outcome, by the same construction, already has a mapped outcome for its own step; the coverage family can only fail because of a DIFFERENT, unresolved need. `automation_engineering/promotion/cp3_decomposition.py::decompose_for_asset` realizes this reframing by EXCLUDING the coverage family from a per-candidate gate entirely, which is mathematically the same result as recomputing coverage over the resolved-needs-only subset and finding this one need already inside it — not a weaker check, the same check correctly scoped to what it can be true or false about for one candidate.

**`duplicate_steps` and the two static customqa checks (`direct_webdriver_action`, `long_method`) decompose differently, and more directly: they already carry real per-class/per-asset attribution in their own message text** (`architecture.py`'s own `_evaluate_one_class`/`_long_method_messages`, one message per offending class; `coverage.py`'s own `_find_duplicate_patterns`, one message per colliding `asset_id`) — `decompose_for_asset` filters those SAME already-computed messages by whether THIS candidate's own `class_name`/`asset_id` is named, no re-parsing or re-scanning performed. Note `duplicate_steps` (this criterion, scanning the post-generation WORKSPACE catalog for Cucumber-ambiguous-glue WITHIN one run) is a DIFFERENT check from ADR-0045 D2(b)'s own duplicate check (content-hash against the TRACKED BASELINE catalog, already per-candidate by construction) — the two are independent and this note decomposes only the former.

**`sonar_quality_gate` does not decompose, and this note is honest about why.** The SonarQube server's own `/api/qualitygates/project_status` reports ONE verdict for the whole scanned Maven project — `SonarQualityGateResult`/`SonarQualityGateCondition` (`cp3/sonar/models.py`) carry no file or class attribution at all. There is no per-class Sonar evidence to filter, because none is produced by the real machinery this platform has today. A whole-project Sonar FAIL is therefore applied to every promotion candidate in the batch uniformly, unchanged from before this note — this is the one CP3 criterion for which "per-asset" cannot be honestly claimed, and this note does not claim it.

### D6 — CP4: static locator health, no SUT dependency (Q3)

CP4 gates on static analysis of generated page-object source alone: locator uniqueness, duplicate-locator detection, dynamic-XPath anti-pattern thresholds, and well-formedness (LLD §16/§17: "Broken Locators: 0," "Duplicate Locators: 0," "Dynamic XPath Count: Threshold," "Locator Uniqueness: 100%," transcribed verbatim). No running browser and no SUT are consulted to compute any of these — they are properties of the source text of a generated page object, checkable without ever launching a driver.

**Live-DOM validation — "does this locator actually match a real element on a running page" — is explicitly not CP4's job.** That is Layer 5's runtime concern, exercised against a real SUT once the suite actually executes, and it is architecturally distinct from CP4 in exactly the way CP4 must stay distinct from it: Layer 3 has **no running-browser or SUT dependency at all**, unlike CP3 (D5, above), which does depend on live infrastructure — a running SonarQube scanner, not a browser. CP4 must not acquire one; a future implementation that reaches for a live driver to validate a locator inside CP4 has moved Layer 5's job into Layer 3, and violates this decision.

### D7 — Test data from Layer 2's specification (S3)

Layer 3 generates Java test-data classes **from** Layer 2's emitted test-data specification (ADR-0043 D7) — it does not re-derive test data, and it does not consume the LLD's own §11 `positiveData`/`negativeData`/`boundaryData` JSON shape, which ADR-0043 already superseded when it superseded the identical shape in the Layer 2 LLD. ADR-0043 D7 locks the specification as "which fields are needed, and for each, whether positive/negative/boundary variants are required" — a handoff contract, not a dataset — leaving Java test-data classes explicitly as "a Layer 3 artifact." This ADR is where that ownership is exercised.

The already-registered `generate-test-data` prompt (verified by ADR-0043 D7: targets `src/test/java/com/automation/utils/`, package `com.automation.utils`, `ConfigReader`-mediated config-driven values) generates against `Constants`/`ConfigReader`/`DataProvider`-shaped output. This must reconcile with the walking-skeleton tracked baseline's own `env.*`/`data.*` `ConfigReader` split (ADR-0037's resolution note: `env()` for environment binding, `data()` for test data and fixture credentials) — the generated `DataProvider` output is `data()`-shaped content, not `env()`-shaped, and must never blur into the SUT-binding boundary ADR-0037 D3 locks (no test-data class may itself resolve an environment URL or credential; that stays `ConfigReader.env()`'s job).

**Test-data generator built; two findings recorded, both discharged (additive, 2026-07-31, the Layer 3 test-data generator build).** (1) **"Already-registered" was imprecise, corrected here.** This Decision's own text (and ADR-0043 D7's) calls `generate-test-data` "the already-registered `generate-test-data` prompt" — true only of the ORIGINAL POC's own prompt catalog (`docs/reference/automation-poc/prompts/generate-test-data.md`); no registration for it ever existed in this platform's actual governed registry (`automation_engineering/prompts/composition.py` — verified directly, zero references before this build). This build performs that registration (`generate_test_data` v1.0.0), reconciling the POC's own stale `ConfigReader.get(...)` call (a method the tracked baseline's real `ConfigReader` never had) against the walking skeleton's actual `env()`/`data()` split. (2) **Layer 2's own D7 specification emission is a locked DECISION, never an IMPLEMENTED one.** A repo-wide search for `TestDataSpec`/`test_data_spec`-shaped code in `feature_engineering/` returns nothing — Layer 2 emits no test-data specification today. `TestDataSpecification`/`TestDataFieldSpec` (`automation_engineering/generation/models.py`) are therefore modeled on the CONSUMING side, matching ADR-0043 D7's own prose contract field-for-field (`required_variants` reusing `PolarityHint`, ADR-0042, unchanged); this generator is built and proven against that contract, not a real Layer 2 emission, because none exists to prove against. The real end-to-end path (Layer 2 emits -> Layer 3 consumes) remains NOT exercisable; closing it is Layer 2's own gap, out of this build's scope. **The reuse question, resolved by investigation, not analogy:** test-data does NOT get ADR-0044 D3's reuse-first treatment — `AssetKind` (`automation_engineering/catalog/models.py`) names exactly three reusable-asset kinds, none of them test data, and this Decision's own D1 lists "Java test-data classes" as a deliverable SEPARATE from the reuse-tracked trio. `automation_engineering/generation/test_data_orchestrator.py` never imports the reuse engine; every specification generates, every time, proven for multiple independent specifications (never a skip). **The env/data boundary is enforced, not merely requested:** a deterministic, orchestration-level guard (`_check_no_env_binding`) raises `TestDataBoundaryError` on any `ConfigReader.env(...)` call or `env.`-prefixed config-key literal in generated output, on top of the prompt's own CONSTRAINTS section asking for the same thing — proven for both a violating and a compliant case. `make test`: 5201 → 5238 (+37: 30 new across the test-data generator/orchestrator test modules, 7 new prompt-registration proofs); `make lint`: clean; mypy (informational): 432 → 432, no rise (`git stash -u` baseline re-verified directly).

**The consumed input is now REAL, not contract-only (additive, 2026-07-31, the Layer 2 test-data specification emission build).** Finding (2) directly above is discharged: Layer 2 now implements D7's own specification emission (`feature_engineering/stage/test_data_spec.py`, additive note on ADR-0043 D7). The RECONCILIATION this closed the gap with: `TestDataSpecification`/`TestDataFieldSpec`, originally defined unilaterally in `automation_engineering/generation/models.py` (this Decision's own prior build, because Layer 2 emitted nothing to consume), now live in `contracts/test_data_specification.py` — the SAME shared cross-layer home `contracts.testable_requirement.TestableRequirement` already uses — with the two Java-shape fields (`target_class_name`/`target_package`) REMOVED from the shared contract (Layer 2 could never honestly supply them; D7's own "not a dataset and not Java" already said so) and replaced by Layer 3's own derivation, `automation_engineering.generation.test_data_orchestrator.derive_test_data_class_name`, computed from `requirement_id` at generation time. **THE END-TO-END PATH IS NOW EXERCISABLE**, proven directly (`tests/unit/test_layer2_layer3_test_data_end_to_end.py`): a real `feature_engineering.stage.test_data_spec.build_test_data_specification` output feeds directly into the real `automation_engineering.generation.test_data_orchestrator.generate_test_data_class`, no adapter, both against a hand-built `data_fields`-populated requirement and against every one of the real saucedemo corpus's 30 requirements (the latter honestly empty, per that build's own finding — reproduced here, not re-litigated). This Decision's own text is unchanged; only the "not exercisable today" status directly above is superseded by this note.

**TBD, resolved at implementation:** the exact specification → Java mapping (which specification fields become which `DataProvider` methods/`Constants` fields). This ADR locks the source (Layer 2's specification, never re-derived) and the boundary (test-data content only, never environment binding); the concrete mapping is deferred (Consequences, below).

### D8 — Prompts, run-state, workspace

**Prompt registry.** Layer 3 uses the shared prompt registry (ADR-0014, `shared/prompts/`) — the same mechanism Layer 2 became a second consumer of (ADR-0043 D4), not a new or parallel registry. The LLD's own §9 "Copilot Prompt Registry" component (reusing existing POC prompts: Generate Step Definitions, Generate Page Objects, Generate Selenium Test, Generate Utility Methods) is realized through this same shared mechanism, not a third bespoke one.

**`PromptCompatibility` generalization — trigger fires here.** `architecture-baseline-v2.md` §4 item 12(b) (via ADR-0043 D4) deferred `PromptCompatibility`'s five Layer-1-named fields' generalization to "whoever next needs a Layer 2 prompt to declare compatibility," later sharpened to an explicit trigger: "generalize when Layer 3's own prompt registration needs its own compatibility dimensions declared — a third, structurally different consumer." **This ADR's own Acceptance is that trigger event:** Layer 3's architecture is now locked, and its prompts (step-definition, page-object, selenium-test, and utility-method generation, per LLD §9, plus `generate-test-data` already registered per D7) are real, imminent registrants against the shared registry. **The generalization itself is not performed by this ADR** — this is a documentation-only freeze that builds no code and registers no prompt — it is deferred to Layer 3's implementation, at the point its first prompt is actually registered against `PromptCompatibility`. See the additive amendment note added to ADR-0043 alongside this ADR, recording the trigger as fired.

**Run-state.** Layer 3 occupies stage 15 of `run_state.json`'s reserved stage table (ADR-0036: `| 15 | Automation Engineering (Layer 3, ADR-0031) | none yet | Not started |`) — this ADR is now that stage's governing ADR, the same relationship ADR-0043 established for stage 14. This ADR does not change ADR-0036's stage table or its resume/idempotency semantics; it specifies what stage 15 does once implemented, mirroring ADR-0043 D8's own idempotency pattern: a `content_hash`-unchanged input (a `.feature` file whose content did not change since the run that last generated automation for it) is a candidate for SKIP, subject to the same two-invariant predicate (hash match **and** the declared output artifacts still exist and are valid) ADR-0036 already establishes platform-wide.

**Workspace.** Generated step definitions, page objects, utilities, and test-data classes land in the untracked per-run workspace (ADR-0037 Path A — the same isolated-copy-of-the-tracked-baseline mechanism Layer 2's `.feature` files already use) — never the tracked baseline directly, for the same reason ADR-0037 D2 already gives: a healing action's (or, here, a regeneration's) blast radius must stay bounded to one run's disposable output. **Promotion from workspace to baseline remains ADR-0037's open TBD** — and is now more motivated than when ADR-0037 recorded it open, since promotion is also how the reuse catalog (D3) actually grows: an asset generated in run N only becomes reusable catalog content in run N+1 if it (or a record of it) survives past run N's own disposable workspace. This ADR does not resolve the promotion mechanism; it records why resolving it is now more consequential than before.

## Consequences

- Layer 3's design is fully locked (D1–D8): the input/output boundary against ADR-0043's Validated Feature Package, the Test Generator's deletion, the semantic reuse-first catalog and its three-part safety model, CP3's coverage-gated/reuse-reported/Sonar-hard-gated shape, CP4's static-only scope, the test-data handoff from ADR-0043 D7, and the shared-registry/run-state/workspace placements — all without redesigning any dependency this ADR cites.
- **What Layer 3 does not own:** Layer 4's suite-level integration governance (orphaned-glue detection, near-duplicate steps across the whole suite, aggregate release decision — ADR-0040 Decision 3); CP5 and CP6 (Layer 4's and Layer 5's own control points respectively — LLD Reviewer's note item S7); Layer 5's live-DOM/runtime locator validation (D6) or its execution/tag-selection mechanism (D2); the promotion mechanism from workspace to tracked baseline (ADR-0037's own open TBD, D8).
- **Additive amendment notes, both recorded alongside this ADR:** ADR-0040 (an additive note near Decision 1 specifying the CP3/SonarQube hard-gate mechanics this ADR locks — the dual generation-constraint role, the stub-vs-live test story — none of which change Decision 1's own table, only specify it in full); ADR-0043 (an additive note at D4 recording that the `PromptCompatibility` generalization trigger has fired — Layer 3's architecture is now locked and it is a real, imminent third registry consumer — without performing the generalization itself, which stays deferred to implementation).
- **The ADR-0037/ADR-0040 "Layer 4 asset" vs. "CP3 evaluator" tension (D5) is reconciled by this ADR's own text, not by amending either source ADR** — both remain correct, read as answering different questions (profile stewardship vs. profile evaluation).
- **Resolved (2026-08-06, additive note at D5): coverage-for-promotion semantics are decomposed per-asset.** D5's own run-level `overall_verdict` is unchanged; a companion additive note on ADR-0045 D2 (this same date) uses this decomposition to gate promotion per-candidate rather than per-run — see both ADRs' own added notes.
- **Open TBDs this ADR does not resolve, each with a stated trigger:**
  - The asset catalog's exact storage location (D3) — resolve at implementation, when the catalog is first built against a real filesystem layout.
  - Semantic-match mechanism, embeddings vs. per-step LLM call (D3) — resolve at implementation; this ADR records a lean toward embeddings, not a lock.
  - The test-data specification → Java mapping (D7) — resolve at implementation, once `generate-test-data`'s registered prompt output is reconciled field-by-field against the specification ADR-0043 D7 defines.
  - The promotion mechanism, workspace → tracked baseline (ADR-0037, restated at D8) — resolve when a future ADR revisits ADR-0037's own open TBD; now additionally motivated by catalog growth (D3), not only by the original promotion question.

## Recommendations (permanent)

1. **No Layer 3 code ever generates a test/runner class, `@RunWith(Cucumber.class)`, or `@CucumberOptions`** — restated as binding on Layer 3 specifically (ADR-0041 D3/Recommendation 1; D2 above).
2. **No semantic reuse binding is ever trusted on confidence alone** — content-hash validation and signature/parameter fit are both mandatory, every time, alongside the confidence threshold (D4). A future implementation that treats the confidence score as sufficient by itself violates this ADR's central decision.
3. **No LLM-judged signal is ever wired into CP3's or CP4's pass/fail path** — restated as binding on Layer 3 specifically (ADR-0040 Decision 2; the semantic match itself is advisory until D4's two deterministic checks verify it).
4. **CP3 never gates on reuse percentage** — report it, never fail a run on it (D5).
5. **CP4 never acquires a running-browser or SUT dependency** — that boundary belongs to Layer 5, permanently, not provisionally (D6).
6. **No test-data value is ever sourced from `SourceArtifact` or resolves an environment binding** — restated as binding on Layer 3's test-data classes specifically (ADR-0037 D3/Recommendation 2; D7 above).

## Ownership, scope, and governance

- **Owns:** Layer 3's full architecture — input/output boundary and scope (D1); the Test Generator's deletion (D2); the asset catalog model and semantic matching strategy (D3); the reuse-safety model (D4); CP3's placement and rule shape, including the SonarQube hard-gate (D5); CP4's placement and static-only scope (D6); the test-data generation boundary (D7); and Layer 3's prompt-registry consumption, run-state stage, and workspace placement (D8).
- **Does not own:** Layer 4's suite-level integration governance or CP5 (ADR-0040 Decision 3); Layer 5's execution, tag selection, live-DOM validation, or CP6 (Consequences, above); the promotion mechanism (ADR-0037's own open TBD); `PromptCompatibility`'s actual generalized field list (deferred to implementation, D8).
- **Governance:** Accepted as an architecture freeze, effective immediately. Authorizes a future Layer 3 implementation milestone to build against D1–D8 without redesigning them. Amends ADR-0040 and ADR-0043 additively (see each ADR's own added note); does not supersede either.
