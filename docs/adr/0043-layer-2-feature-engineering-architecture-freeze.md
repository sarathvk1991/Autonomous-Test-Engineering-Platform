## Problem

ADR-0034 froze six architectural properties of the Layer 1 → Layer 2 boundary and explicitly deferred the field list, the acceptance-criteria structure, and "everything Layer 2-specific" to "Layer 2's architecture-freeze ADR... with Layer 2's own designers as the deciding voice" (ADR-0034 §D5, Resolution path). ADR-0042 has since resolved the field list. ADR-0040 has already carved CP2 out of a previously-assumed Layer 4 and placed it in Layer 2, in-layer, deterministic-gate-only. ADR-0037/ADR-0041 have already frozen where Layer 2's `.feature` files land and what they run against. What remains genuinely undecided — decomposition, scenario identity, the lint-runtime choice, prompt reuse, the remediation loop's exact shape, the step-vocabulary mechanism, and the test-data ownership boundary — is exactly the set of questions ADR-0034 §D5 pointed at this document to answer. The committed LLD (`docs/proposals/layer-2-feature-engineering-lld.md`) is evidentiary input toward that, not itself approved design — several of its sections are already superseded, per its own Reviewer's note, by decisions made in ADR-0034, ADR-0040, and ADR-0042 since it was transcribed.

This ADR is also the first ADR proposed against ADR-0032's stated freeze-lifting procedure, whose first precondition names this exact layer ("Layer 2... has reached Runtime Integration"). Whether that precondition is actually satisfied is investigated directly in D8, not assumed.

## Decision

### D1 — Input and decomposition

Layer 2 consumes `TestableRequirementSet` (ADR-0034/ADR-0042) and **nothing else** from Layer 1. `AnalysisResult` is not a Layer 2 input — ADR-0034 Recommendation 1 already forbids any component outside Layer 1 from importing or depending on `AnalysisResult`; this ADR does not reopen that boundary, it restates it as binding on Layer 2 specifically.

**One `TestableRequirement` maps to exactly one `.feature` file** (ADR-0042 Decision 1(b), restated here as this ADR's own binding decision): `title` becomes the Gherkin `Feature:` name (≤ 70 chars, `.gherkin-lintrc:17`, re-verified); `component` determines the generated file's path. Decomposition is deterministic and reuses the requirement's own identity — no new decomposition logic, no LLM decomposition step.

Layer 1 emits `risks[]` (at the `TestableRequirementSet` level, per ADR-0042's structural correction note), never scenarios. **Converting a risk into one or more scenarios is Layer 2 work exclusively** — ADR-0042's own boundary decision (a), restated as binding: "Scenario generation lives in exactly one layer." No risk-to-scenario logic exists in Layer 1, and none may be added there under ADR-0032's freeze.

### D2 — Scenario identity and traceability tags

`SCN-*` ids are platform-assigned, content-addressed, and never LLM-assigned — the same discipline `REQ-*`/`AC-*`/`RSK-*` already carry (ADR-0042 Decision 2). This ADR extends that shared scheme with a third pattern: `SCN-<AC short>-<2-digit ordinal, stable within the acceptance criterion>`, content-addressed over the scenario's own canonical content plus its parent `AC-*` id, using the same shared normalization function (casefold, collapse whitespace, strip punctuation) ADR-0042 Decision 2 already establishes for every other ID type. **Assigned AFTER the remediation loop** (D5), per ADR-0042 Decision 1(c)'s own reasoning: remediation can split or rename scenarios, and an id assigned before that would be orphaned by the split/rename it is meant to survive.

Traceability is emitted as Gherkin **tags** in the `.feature` file, not only a sidecar: `@REQ-*` at Feature level, `@SCN-*` and `@AC-*` (one or more) at scenario level. These flow into `messages.ndjson` (ADR-0041 D6) automatically, giving Layer 6 traceability with no extra plumbing. `traceability.json` (LLD §20) becomes a **derived index**, built by reading the emitted tags back out, never the source of truth — this is what the LLD's own Reviewer's note already points at ("Traceability IDs are emitted as Gherkin tags in the artifacts themselves; `traceability.json` becomes a derived index").

**Homogenous-tag hoist rule.** `.gherkin-lintrc`'s `no-homogenous-tags` rule (verified: `"no-homogenous-tags": "on"`) flags any tag present on every scenario in a feature. `@REQ-*` is, by construction, identical across every scenario in one feature (D1's one-requirement-one-feature rule), so it is *always* homogenous and **must** be written at Feature level, never per-scenario — not a style choice, a direct consequence of a lint rule already committed to the config. `@SCN-*` and `@AC-*` are scenario-scoped by construction and are therefore never homogenous, so they stay at scenario level. This is the one place tag strategy and lint collide, and it is resolved by construction, not by a runtime check.

### D3 — Gherkin linter: runtime and rule fidelity

**Runtime decision:** a Python port of the 17-rule set over the official Cucumber Gherkin parser, not a retained npm `gherkin-lint` dependency. This is not a fresh decision by this ADR — it transcribes the already-recorded owner position in the LLD's own Reviewer's note ("§12... Rules to be ported to Python over the official Cucumber Gherkin parser, preserving `.gherkin-lintrc` verbatim as the config contract. Rule set is not to be extended," re-read directly), which this ADR locks formally. Rationale: avoids a third language runtime (Node/npm) alongside the JDK/Maven stack ADR-0041 already commits the generated suite to, and alongside this platform's own Python runtime — two runtimes (Python platform, JDK generated suite) is already the ADR-0041 baseline; a third, existing solely to run `gherkin-lint`, is removed by this decision rather than added.

`.gherkin-lintrc` is preserved **verbatim** as the config contract — re-verified directly: 17 keys (`no-unnamed-features`, `no-unnamed-scenarios`, `no-empty-file`, `no-files-without-scenarios`, `no-dupe-feature-names`, `no-dupe-scenario-names`, `no-duplicate-tags`, `no-homogenous-tags`, `no-scenario-outlines-without-examples`, `no-examples-in-scenarios`, `no-partially-commented-tag-lines`, `no-trailing-spaces`, `no-multiple-empty-lines`, `new-line-at-eof`, `indentation`, `name-length`, `scenario-size`), same rule names, same config shapes — so the POC's own committed file drops into the tracked baseline unchanged. The 17 rules are **ported, not reinvented and not extended**; an 18th rule requires a future ADR.

Structural facts the port must honor, verified against the committed config directly:

- **5 rules operate on raw source text, not the parsed AST alone**, because the Gherkin AST discards exactly what these rules check: `no-trailing-spaces`, `no-multiple-empty-lines`, `new-line-at-eof`, `no-partially-commented-tag-lines`, `indentation`.
- **`no-dupe-feature-names` is cross-file by definition** — a duplicate feature *name* can only be detected by comparing every feature file in the workspace — so lint runs as a **workspace-scoped stage** over the full generated set, never invoked per-file in isolation for this rule.
- **`no-dupe-scenario-names` is scoped `in-feature`**, per the committed config (`"no-dupe-scenario-names": ["on", "in-feature"]`, verified) — duplicate scenario names are checked only within one feature file, not across the workspace.

**Correction note (additive, 2026-07-27).** During the Layer 2 Gherkin-linter implementation (the first Layer 2 build against this ADR), the "5 rules operate on raw source text" claim above was re-verified against upstream `gherkin-lint`'s actual source (`src/rules/*.js`) and empirically against the committed port (`feature_engineering/gherkin_lint/rules.py`) — the count is **3, not 5**: `no-trailing-spaces`, `no-multiple-empty-lines`, and `new-line-at-eof` are the only rules that read raw source lines (`SourceFile.lines`). `indentation` operates entirely on AST `location.line`/`location.column` fields, and `no-partially-commented-tag-lines` operates entirely on the AST's `tag.name` string (the `#` character survives verbatim in the parsed tag name — confirmed directly against the parser, not assumed) — neither ever reads a raw line. This corrects the supporting rule-count claim only; it does not change this Decision. The architectural requirement this bullet list exists to establish — "do not build an AST-only linter that can't see [raw-source information]" — is unchanged and is satisfied regardless of the count: the committed port gives every one of the 17 rules uniform access to both `SourceFile.lines` and `SourceFile.feature` (the AST), so a rule that turns out not to need the raw lines simply doesn't reference them, rather than being unable to. The finding and its evidence are recorded in `feature_engineering/gherkin_lint/rules.py`'s module docstring and in `tests/unit/test_gherkin_lint_rules.py` (`RAW_SOURCE_RULES`, `TestRawSourceRulesCatchWhatAstAloneMisses`).

### D4 — Prompts: registry and conversion

Layer 2 uses the **existing** governed prompt registry (ADR-0014: canonical models, `PromptRegistry`/`PromptLoader`, SHA-256-verified `versions/manifest.json`, sealed OPEN→SEALED lifecycle). It does **not** build the LLD's own proposed second registry (§5/§7/§20's `prompt-registry.json`) — that shape is superseded per the LLD's own Reviewer's note.

ADR-0014 was written scoped to Layer 1 (CAP-071/072/073); its registry package lives at `requirement_intelligence/prompts/` today (verified by directory listing). This ADR establishes Layer 2 as a second consumer and directs that the registry be extracted to a shared, platform-level location so neither layer's package tree owns code the other imports directly. **This extraction is implementation work, not decided or executed by this pure-architecture-freeze ADR** — and it is flagged, not waved through: physically relocating code out of `requirement_intelligence/` is not literally one of ADR-0032's five enumerated carve-outs (emitting `TestableRequirement`; run/stage state integration; the two named ADR-0033 renames; bugfixes; tests). It most resembles carve-out 3's own rationale — a rename/relocation with no behavior change is not "growing" Layer 1's judgement capability — but ADR-0032 enumerates carve-out 3 as closed to the two *named* ADR-0033 renames specifically, not renames-in-general. **This ADR does not resolve that gap.** Layer 2's future implementation milestone must either (a) show the extraction is a no-behavior-change relocation consistent with carve-out 3's own stated rationale and proceed on that reading, or (b) treat it as requiring a properly-lifted freeze first. Which reading governs is left to whoever executes that implementation, informed by this note — not guessed here. **This decision is forced at the point Layer 2 implementation first needs to import the prompt registry; it must be resolved then — as either an ADR-0032 carve-out-3 relocation or a freeze-lift precondition — and not deferred past that point.** An additive amendment note recording Layer 2 as a second consumer is added to ADR-0014 (see Consequences).

**Forcing-clause resolution note (additive, 2026-07-27).** The clause above fired: registering Layer 2's converted prompts required importing this registry, which is exactly the forced point. Resolved as **(a), the carve-out-3 reading** — the framework mechanism (`PromptRegistry`, `PromptLoader`, exceptions, the governed template contract, and the canonical models) is generic, behavior-free infrastructure with no Layer-1 judgement logic (verified directly: `PromptLoader.load()` already took `versions_dir` as a caller-supplied parameter, and every `PromptRegistry` instance already carried no Layer-1-specific state), so relocating it is a rename with no behavior change, not growth of a Layer 1 capability — reading (b), a freeze-lift precondition, would have been a category error here, since importing generic infrastructure adds no new Layer 1 CAP number. The mechanism relocated to `shared.prompts.{framework,models}`; Layer 1's own content (`composition.py`'s hardcoded registrations, `versions/`, the constants/templates/builder) stayed at `requirement_intelligence/prompts/` unchanged, now itself a consumer of the shared mechanism — the same position Layer 2 is in. Two Layer-1-shaped elements moved unchanged rather than being generalized (`ARTIFACT_CONTEXT_PLACEHOLDER`'s naming; `PromptCompatibility`'s five Layer-1-named fields) — open items, not resolved here (`architecture-baseline-v2.md` §4). Verified byte-identical: 4820 tests before and after, golden-baseline SHA-256 determinism passing. See ADR-0014's own relocation note for the consumer-side detail.

The five POC prompt assets — `generate-feature.md`, `fix-gherkin-lint.md`, `refactor-feature.md`, `generate-test-data.md`, `validate-generated-feature.md` — are **agentic slash-commands**, re-verified directly: each opens with a `**Command:** /...` line and closes with a VALIDATION section invoking shell commands (`npm run lint:gherkin:html`, `mvn clean verify -Dheadless=true`) and, in `validate-generated-feature.md`'s case, a "Next Recommended Action" table chaining to the next slash command. Their **CONSTRAINTS blocks are the reusable asset** this ADR carries forward — verified content: `generate-feature.md`'s length/tag/duplication/indentation constraints restate `.gherkin-lintrc` rules D3 already locks, plus a business-readability instruction and "Ensure step text aligns with reusable step definitions (avoid overly specific phrasing)," which D6 makes enforceable. Their file-IO, shell invocation, `npm run`, and next-command-chaining scaffolding is **stripped**: the platform, not the prompt, owns file placement, lint execution, and loop orchestration; the prompt generates content only.

`generate-feature.md`'s `{{REQUIREMENT}}` prose blob (verified: `INPUT` section reads `Requirement:\n{{REQUIREMENT}}`) is replaced by a **structured `TestableRequirement` input** — the platform serializes the `TestableRequirement`'s `title`/`narrative`/`acceptance_criteria[]`/`polarity_hints` fields into the prompt in place of free prose. Step text is still generated freely by the LLM; the D2 tags are added deterministically by the platform *after* generation, never by the LLM — consistent with "IDs are platform-assigned, never LLM-assigned" (ADR-0034 property 1, ADR-0042 Decision 2, extended to `SCN-*` by D2 above).

Provider-agnostic via `llm_factory` (ADR-0014 §Context 2: "provider agnosticism is already established... this invariant must be preserved"; the LLD's §8/§14 Azure OpenAI references are superseded per its own Reviewer's note). No vendor name appears in any Layer 2 contract or prompt; Gemini is in use, Azure is pending — the same superseded-items list this ADR binds to throughout.

### D5 — CP2 and the bounded remediation loop

Pipeline order: **generate → deterministic formatter → lint → [LLM remediate → re-lint], max 2 attempts → assign `REQ`/`AC`/`SCN` tags (D2's hoist rule) → final lint → CP2 gate.** The deterministic formatter fixes the pure-formatting lint rules (the 5 raw-text rules named in D3, plus `indentation`) at zero LLM cost — these are mechanical corrections, not judgement.

**CP2 gates deterministically only** (ADR-0040 Decision 2, binding, not re-decided here): lint result; acceptance-criteria coverage (every `AC-*` on the input `TestableRequirement` has at least one mapped `SCN-*`); tag presence (`@REQ-*`/`@SCN-*`/`@AC-*` all present per D2); duplicate detection (the `no-dupe-*` rules). The LLD's own §15/§16 "Business readability" and "Step reusability" checks (verified, named identically in `validate-generated-feature.md`'s Checks table) remain **advisory** — they may trigger LLD §17's human-in-the-loop conditions (verified: "Feature generation confidence low," "Generated feature changes business intent," etc.), but never gate CP2's pass/fail path. This is ADR-0040 Decision 2 applied to CP2's specific rule catalogue, which ADR-0040 itself deferred to "Layer 2's... future LLD" — this document's job.

**Two rules are non-remediable**: `no-empty-file`, `no-files-without-scenarios` (both verified `"on"`). A violation of either means generation itself failed — there is no content to remediate — so these escalate directly to human-in-the-loop rather than entering the 2-attempt loop.

**Dropped from the Layer 2 port**: "must not break step definition mappings," verified present in both `fix-gherkin-lint.md` ("Generated changes must not break step definition mappings") and `refactor-feature.md` ("Do not break existing step definition mappings — all steps must continue to resolve"). Step definitions do not exist at the point CP2 runs — they are a Layer 3 artifact, generated only after a feature passes CP2. The real equivalent check (near-duplicate/orphaned step definitions) belongs to Layer 4's suite-level integration governance (ADR-0040 Decision 3) and, pre-generation within Layer 2 itself, to D6 below.

### D6 — Step vocabulary (prevents Layer 3 glue explosion)

**Governing citation.** The near-duplicate-step check below is a CP2 platform check — CP2 belongs to Layer 2 and gates deterministically, per ADR-0040 Decision 1's placement and Decision 2's deterministic-gate discipline; ADR-0040 explicitly defers CP2's own rule catalogue to "Layer 2's... future LLD," which is this ADR's job to fill. The step-vocabulary index itself, however, is a **new Layer 2 decision this ADR originates** — no prior ADR names or requires it; it exists to make the near-duplicate-step check possible and to give `generate-feature.md`'s own otherwise-unenforced reuse instruction a real mechanism.

Maintain a controlled step-vocabulary index: canonical step phrasings plus their origin. Generation reuses an existing phrasing where one matches a step's intent and extends the vocabulary only when none does. The most-relevant existing steps are injected into the generation prompt as context, so the LLM sees what already exists before writing new step text.

**"No near-duplicate steps" is a CP2 platform check — code comparing generated step text against the vocabulary index — not a new Gherkin lint rule.** This keeps D3's 17-rule set intact; `gherkin-lint`'s rule model has no concept of a cross-run vocabulary, and inventing an 18th rule for this would trip D3's own future-ADR gate. This is the mechanism behind `generate-feature.md`'s otherwise-unenforced CONSTRAINTS instruction (verified: "Ensure step text aligns with reusable step definitions (avoid overly specific phrasing)") — that sentence exists in the prompt today with nothing to check it; D6 gives it a real enforcement path.

### D7 — Test data boundary (resolves the three-places-one-owner problem)

Layer 2 owns `Examples:` tables: small, discriminating values written inline in the `.feature` file for `Scenario Outline:` cases (LLD §10, un-superseded).

Layer 2 emits a test-data **specification** — which fields are needed, and for each, whether positive/negative/boundary variants are required, seeded by `AcceptanceCriterion.polarity_hints[]` (ADR-0042, already `POSITIVE`/`NEGATIVE`/`BOUNDARY`). This specification is a handoff **contract**, not a dataset and not Java — it supersedes LLD §11's own `positiveData`/`negativeData`/`boundaryData` JSON shape, per the Reviewer's note.

**Java test-data classes are a Layer 3 artifact.** `generate-test-data.md` (re-verified: targets `src/test/java/com/automation/utils/`, package `com.automation.utils`, `ConfigReader`-mediated config-driven values) is a Layer 3 prompt, not Layer 2's. This ADR does not own Java test-data classes; it defines the specification Layer 3 consumes as input.

### D8 — Run-state, output location, and the freeze lift

Layer 2 occupies stage 14 of `run_state.json`'s reserved slot table (ADR-0036, verified: `| 14 | Feature Engineering (Layer 2, ADR-0031) | none yet | Not started |`). This ADR does not change ADR-0036's stage table; it specifies what stage 14 does once implemented — the same way every other live stage's own governing ADR already does.

**Idempotency via `content_hash`** (ADR-0042 Decision 3, already locked as "the field a future implementation uses to decide whether ADR-0036's stage may be marked SKIPPED on resume"): regenerate only the `.feature` file(s) for a `TestableRequirement` whose `content_hash` changed since the run that last produced this run's inputs; an unchanged requirement is SKIPPED, subject to the two-invariant skip predicate this platform's ADR-0036 implementation already establishes (hash match **and** the declared output artifact exists and is well-formed — hash match alone is never sufficient). This is where "update-feature" (regenerate a changed feature) vs. "generate-feature" (produce a new one) fires — the same content-hash check distinguishes them; it is not a separately-decided branch.

Generated `.feature` files land in the untracked per-run workspace, at `src/test/resources/features/` **within the tracked module** (`test-suite-baseline/` — ADR-0037's now-resolved baseline path, and ADR-0041's `@SelectClasspathResource("features")`, which requires exactly this path to resolve features at all). The Validated Feature Package (LLD §3/§18's reports, the derived `traceability.json` per D2, and the CP2 result) lands in the run directory, alongside `run_state.json`/`manifest.json`, per ADR-0036's existing artifact-path discipline. Neither location is new: ADR-0037 already locked the tracked/workspace split and ADR-0036 already locked the run directory as the artifact home; this ADR places Layer 2's specific outputs into those two pre-existing homes.

#### Freeze lift — finding: precondition not met, staged not immediate

ADR-0032's lifting procedure requires, as its first stated precondition: **"Layer 2 (Feature Engineering) has reached Runtime Integration"** (ADR-0032, "How the freeze is lifted," item 1 — quoted verbatim, re-read directly for this ADR) — a specific stage in the six-stage lifecycle ADR-0032 itself cites: **Architecture Freeze → Deterministic Implementation → Runtime Contract Freeze → Runtime Integration → Execution Package Integration → Golden Rebaseline.**

**This ADR is Layer 2's Architecture Freeze — stage 1 of 6, not stage 4.** No Layer 2 code exists (verified: `feature_engineering/` remains the single-commit placeholder package from the repository's initial commit). Runtime Integration cannot have occurred for a layer with zero implementation. **Precondition 1 is not met at ADR-time.** Preconditions 2 (Architecture Review Board approval of the specific lifting ADR) and 3 (naming which Layer 1 CAP number(s) are authorized) are consequently moot here — there is nothing yet to bring before that body as a lifting decision, and no CAP number is proposed by this ADR, because no new Layer 1 judgement capability is being requested.

**This ADR therefore does not lift ADR-0032's freeze.** Claiming otherwise would assert a precondition plainly false against the repository's current state — exactly the kind of unverified assertion this platform's own review discipline exists to catch.

**One clarification that matters more than it first appears:** ADR-0032's freeze restricts only **Layer 1's** growth (no new Layer 1 CAP number). It never restricted Layer 2 from being architected or built in the first place — Layer 2 needed its own architecture-freeze ADR (this one), not a Layer 1 freeze lift, to begin. **Building Layer 2 against D1–D8 is therefore authorized by this ADR's own Acceptance alone**, exactly as every other pure architecture-freeze ADR in this repository already authorizes its own layer's implementation (ADR-0034, ADR-0036, ADR-0037, ADR-0041, ADR-0042 all follow this same pattern: "Runtime status: Not applicable... a future implementation milestone builds against this ADR"). The freeze-lift question and Layer 2's buildability are orthogonal; conflating them would be a new error, not a correction of one.

**Sequencing this ADR proposes** (items 2–3 belong to the Architecture Review Board and to whichever future ADR actually lifts the freeze — not to this document):

1. This ADR (Architecture Freeze) — Accepted, effective now. Authorizes a future implementation milestone to build Layer 2 against D1–D8.
2. Once that implementation reaches Runtime Integration (the same lifecycle stage ADR-0032 cites), a **separate, future, numbered ADR** — not this one — is proposed to lift ADR-0032's freeze, satisfying all three of its stated preconditions, including explicitly naming which Layer 1 CAP number(s) it authorizes.

**Until that future ADR exists, ADR-0032's freeze remains in full force, unmodified, restricting only Layer 1.** No new Layer 1 CAP number is authorized by this ADR, directly or by implication.

## Consequences

- Layer 2's design is fully locked (D1–D8): ADR-0034's six properties, ADR-0042's field list, ADR-0036's stage-14 slot, ADR-0037/ADR-0041's suite target, and ADR-0040's CP2 placement are all satisfied without redesigning any of them.
- **ADR-0032's freeze is not lifted by this ADR** (D8) — restated here for visibility, since the task that produced this ADR was framed as lifting it, and the finding that it does not is load-bearing.
- ADR-0014 gains a second consumer (Layer 2); the registry's future physical relocation to a shared platform service is flagged, not decided or executed, pending Layer 2 implementation and the ADR-0032 carve-out question (D4).
- **CAP-087/Layer 2.5's placement is explicitly engaged, not merely restated, and remains open.** ADR-0042 Recommendation 4 requires any future ADR touching this placement to address, not just cite, Decision 7's two conflicts. Addressing them: this ADR's own Layer 2 stays bound to `TestableRequirementSet`-only input (D1) and unconditionally Cucumber-committed output (nothing in D1–D8 introduces a renderer abstraction) — the same two structural facts Decision 7 already found CAP-087 in conflict with. Nothing decided here changes either boundary, so the conflicts are unchanged and the question remains open, for the reasons Decision 7 already gave. Precisely what would resolve each: **conflict (a)** (CAP-087's dependency boundary bypassing `TestableRequirementSet`) resolves either by a redesign of CAP-087's own dependency boundary — ADR-0030's call, per ADR-0042 Decision 7's own attribution — or by a future amendment relaxing this ADR's D1 input-boundary lock; **conflict (b)** (CAP-087's renderer-agnostic Specification Model vs. this ADR's unconditional Cucumber commitment) resolves either by CAP-087 abandoning its renderer-agnostic model or by a future amendment to this ADR's D1/D7 introducing a renderer abstraction. Neither lever is pulled here — not restated citation, but not a resolution either.
- The LLD's superseded sections (Azure OpenAI, `riskBasedScenarios`, `prompt-registry.json`, LLM-judged CP2, the flat requirement model, `traceability.json` as source of truth) are formally closed by binding every one of them to its superseding decision throughout D1–D8, not merely noted as superseded.
- The Layer 2 → Layer 3 handoff (features plus a test-data specification) is defined only from Layer 2's side (D1, D7); Layer 3's own future architecture-freeze ADR must independently confirm it can consume what this ADR commits to producing.

**What this ADR does not own:**
- Layer 3's Java generation (page objects, step definitions, Java test-data classes) — a future Layer 3 architecture-freeze ADR's job.
- CP3 (SonarQube on generated Java) — ADR-0040 Decision 1's placement stands; CP3's own rule catalogue is Layer 3's.
- The promotion mechanism (workspace → tracked baseline) — ADR-0037's remaining open TBD, unaffected here.
- Layer 6's NDJSON consumption itself — ADR-0041 D6 already owns that; this ADR only emits the tags (D2) Layer 6 will eventually read.
- CAP-087/Layer 2.5's placement — engaged, not resolved (see above); remains ADR-0031 §D4 / ADR-0042 Decision 7's open question.
- The physical extraction of ADR-0014's prompt registry to a shared location, and whether that requires an ADR-0032 carve-out or a properly-lifted freeze — flagged (D4), not decided.

## Recommendations (permanent)

1. **No Layer 2 code ever imports or depends on `AnalysisResult`** — `TestableRequirementSet` is the only sanctioned entry point (ADR-0034 Recommendation 1, restated as binding on Layer 2 specifically).
2. **No `SCN-*` id is ever assigned before the remediation loop completes** (D2/D5) — assigning early and re-assigning after a split or rename is not a substitute for this ordering.
3. **No LLM-judged check is ever wired into CP2's pass/fail path** (ADR-0040 Recommendation 1, restated as binding on Layer 2 specifically).
4. **No 18th Gherkin lint rule without a future ADR** (D3) — the 17-rule set is closed, not merely "currently" 17.
5. **No Java code, and no test dataset (as opposed to a specification), is ever produced by Layer 2** — that boundary belongs to Layer 3 (D7), permanently, not provisionally.
6. **Any future ADR touching CAP-087's placement must engage the two structural conflicts** Decision 7 (ADR-0042) and this ADR's Consequences both restate — citing them again without addressing them is not a resolution (ADR-0042 Recommendation 4).

## Ownership, scope, and governance

- **Owns:** Layer 2's full architecture — input and decomposition (D1); scenario identity and tag-based traceability (D2); the Gherkin-lint port's runtime and rule fidelity (D3); prompt reuse and conversion (D4); CP2's placement and bounded remediation loop (D5); the step-vocabulary mechanism (D6); the test-data specification boundary (D7); and Layer 2's run-state stage and output-location placement (D8, first half).
- **Does not own:** Layer 3's generation, CP3, the promotion mechanism, Layer 6's own NDJSON consumption logic, CAP-087/Layer 2.5's placement (engaged, not resolved), or the prompt registry's physical relocation mechanism (flagged, not decided) — see Consequences for each.
- **Governance:** Accepted as an architecture freeze, effective immediately. **Does not lift ADR-0032's freeze** (D8) — that remains a distinct, future, separately-Accepted ADR's job, gated on Layer 2 reaching Runtime Integration. Authorizes a future Layer 2 implementation milestone to build against D1–D8 without redesigning them.
