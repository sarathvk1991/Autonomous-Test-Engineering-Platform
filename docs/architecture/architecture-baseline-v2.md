## 1. Purpose

This is the single page a reader consults to answer "what is locked, and what is still open." It was created because nine architectural decisions were recorded in one sitting (2026-07-24), each with its own TBD items — without one index, a reader would have to open all nine ADRs to know what remains undecided.

## 4. Open questions this baseline does not resolve (consolidated from the TBD column)

1. **Sharpened by ADR-0042 Decision 7, still open.** Where does ADR-0020's Layer 2.5 (Executable Specification Engineering, CAP-087, Proposed, no code) fit under ADR-0031's model? Evaluated against ADR-0031's Layer 2 (Feature Engineering) and found **materially different**, not a naming collision: (a) CAP-087's own frozen dependency boundary consumes `RequirementEnhancementResult`/`GroundingResult`/`ValidationResult`/`RecommendationResult`/`LearningResult` directly — exactly the Layer-1-internal artifacts ADR-0034 Recommendation 1 forbids anything outside Layer 1 from depending on, bypassing the `TestableRequirementSet` boundary ADR-0034/ADR-0042 froze; (b) CAP-087's output is a renderer-agnostic Specification Model (Cucumber only "the first reserved renderer target"), while ADR-0031's Layer 2 is unconditionally Cucumber-committed. A future resolution must address both conflicts explicitly, not merely restate the question. Left to Layer 2's own future architecture-freeze ADR, or a CAP-087-specific revision.
2. ~~What is `TestableRequirement`'s and `TestableRequirementSet`'s exact field list, hash algorithm, and `supersedes`-detection mechanism?~~ **Field list and hash algorithm resolved by [ADR-0042](../adr/0042-testablerequirement-field-specification.md).** The `supersedes`-detection mechanism remains open — ADR-0042 Decision 5 records it as blocked on a cross-run requirement index ADR-0036's filesystem-only model does not provide; no implementation may invent one before a future ADR resolves this.
3. ~~Is `canonical_requirement.py`'s `SourceRef` salvaged into `TestableRequirement`, or discarded with the rest of the file?~~ **Resolved by [ADR-0042](../adr/0042-testablerequirement-field-specification.md) Decision 4**: salvaged, using its actual `system`/`external_id`/`url` shape. Blocks one item of ADR-0035's removal list no longer — that item is unblocked (not yet executed).
4. What is the exact `run_id` scheme, `run_state.json` schema, and lockfile mechanism? Deferred to ADR-0036's future implementation.
5. Does Layer 7 (Governance Dashboard) genuinely participate in the per-run stage sequence, or is it a separate cross-run service? Structurally unresolved by ADR-0036 §D5.
6. ~~What is the concrete Java stack (build tool, Java version, Cucumber-JVM version, runner, browser-automation and assertion libraries, reporter) for the generated suite?~~ **Resolved by [ADR-0041](../adr/0041-java-stack-for-the-generated-test-suite.md)**: Maven, Java 21, BOM-managed JUnit/Cucumber versions, JUnit Platform Suite runner, JUnit Jupiter–only assertions, Selenium 4.25.0 (Selenium Manager, no WebDriverManager), three-reporter split. ADR-0037's other two TBDs (tracked baseline's exact repo path; promotion review mechanism) remain open.
7. Is ADR-0039 (Jenkins, execution backend) ratified? It is Proposed only — nothing in Layer 4 or Layer 5's future architecture may be built against it until it is Accepted.
8. How does an asynchronous, Jenkins-delegated Layer 5 stage fit the otherwise-synchronous stage model ADR-0036 defines? Explicitly left to Layer 5's own future architecture-freeze ADR (ADR-0039 §D2).

## 5. How to use this page

- To find out whether a specific decision is locked, find its row above and read its own ADR — this page's summary is not a substitute for the ADR.
- To find out what remains open before a given layer can be built, read that layer's TBD column entries and §4's consolidated list.
- This page is updated whenever a future ADR changes, supersedes, or resolves a TBD item recorded here — by adding a row (new decision), editing a row's Status/TBD columns (a decision changed or a TBD resolved), or adding a note under §3 (a non-ADR state change, like a status-line edit or a register update).
