## 1. Purpose

This is the single page a reader consults to answer "what is locked, and what is still open." It was created because nine architectural decisions were recorded in one sitting (2026-07-24), each with its own TBD items — without one index, a reader would have to open all nine ADRs to know what remains undecided.

Layer 3 (`automation_engineering/`) has six independently well-tested subsystems — catalog (`catalog/scanner.py::reconcile`), reuse (`reuse/engine.py::decide_reuse`), generation (four independent orchestrator functions, one per asset kind, no whole-feature entry point), CP3 (`cp3/gate.py::evaluate_cp3`), CP4 (`cp4/gate.py::evaluate_cp4`), promotion (`promotion/outcomes.py::promote_outcome` + `promotion/mechanism.py::apply_promotion`/`stage_promoted_assets`) — but **nothing chains them.** Verified directly: `app/api/router.py` line 21 is a commented-out `# api_router.include_router(automation_engineering_router)`; no CLI subcommand imports `automation_engineering`; run-state stage 15 (`automation_engineering`, per ADR-0036) sits at `status: pending` in every run's `run_state.json`, always, including this one; `automation_engineering/README.md` still reads "Status: Planned (Phase 3 — not implemented)," stale relative to the tested code underneath. What a real entry point requires, confirmed by direct source reading rather than assumed: deriving `GherkinStepNeed`s (text/step-type/captures) from real `.feature` text in the untracked per-run workspace (nothing in the repo does this derivation today); materializing a real, on-disk, buildable Maven project with generated Java already written into it before CP3 can be called (CP3 itself writes nothing); reconciling that CP3/CP4 verdicts are whole-run batch results (`AssetGateOutcomes`), not per-asset; and wiring promotion's direct `test-suite-baseline/` writes + `git add` (never `git commit`) into run-state stage 15. This is architecture — a deliberate, reviewed build, per this ADR's own existing item 14(a)/(b) deferrals above — not something to improvise inside a live integration run; none was written for this run. The live SonarQube server this run verified as reachable/authenticated/submission-capable (item 17 above) is ready for CP3 to reach the moment a driver exists, independent of when the `customqa:*` profile gap (item 18) is separately closed. **Owner:** Layer 3 wiring (a future stage-15 CLI/API/run-state integration task, `automation_engineering`). **Trigger to resolve:** a dedicated, reviewed build task — not an integration run — that adds the missing orchestration and, per ADR-0036, wires stage 15 into `run_state.json`.

21. **New (2026-08-04), from the F4 discovery task — item 18's `customqa:*` gap is only PARTLY a "create the profile" task; the two rules are different kinds of things.** Full evidence and the per-rule decision surface are recorded as additive notes directly on the two ADRs that specify the profile, not duplicated here: ADR-0037 Recommendation 3 ("Discovery note, additive, 2026-08-04") and ADR-0044 D5 ("Discovery addendum, additive, 2026-08-04"). Summary: `customqa:long-method` is cheaply real — it IS the built-in `java:S138` ("Methods should not have too many lines," a configurable `max` parameter, verified via this integration's live server) — a profile activating it at `max=40` is a normal, versionable SonarQube profile export, exactly as ADR-0037/ADR-0044 already describe. `customqa:direct-webdriver-action` is NOT one existing rule and cannot be enabled the same way: no Selenium/architecture/layering rule exists in this server's Java catalog, and no custom-analyzer-plugin extension point was found to exist on it at all — the only genuinely native path found is composing a TEMPLATE rule (`java:S2253`/`S3688`, "disallowed methods/classes," global-only) with a separate project setting (`sonar.issue.ignore.multicriteria`) to exclude the ban for `com/automation/pages/**` — real, but a file-path approximation of an architectural constraint, not an exact expression of it, and it lives in project settings rather than quality-profile content. **The honest state: `customqa:*` is partly-aspirational, not fully.** One rule is cheap and real; the other has three legitimate paths (native rule-plus-exclusion composition, a custom Sonar plugin — heavyweight, unconfirmed as even supported here, or a static Python check inside Layer 3 itself, the same posture ADR-0044 D6/CP4 already uses for locator health) and choosing among them is a DESIGN decision, not a config task — explicitly not made by this discovery. No profile was created and no check was written; this item is discovery only. **Owner:** ADR-0037 (profile-artifact existence) / ADR-0044 D5 (which of the three paths `direct-webdriver-action` takes) jointly. **Trigger to resolve:** a future task decides `direct-webdriver-action`'s path (composed-native / custom-plugin / static-Python) and, together with activating `S138` at `max=40`, authors the actual `customqa:*` profile artifact item 18 already tracks as missing.

    **DECIDED (2026-08-04, the F4 revision — Path A, documentation-only, nothing built yet).** `direct-webdriver-action`'s path is chosen: a static Python check in Layer 3, not Sonar in any form (not the rule-plus-exclusion composition, not a custom plugin) — full rationale in ADR-0044 D5's own "Decision note" (this same date), with ADR-0037 Recommendation 3's "Companion note" (this same date) recording the consequence that the eventual `customqa:*` Sonar profile artifact will only ever contain the Sonar-expressible subset (`long-method`). CP3's own gate is now specified as a composite: the Sonar quality gate AND Layer 3's static architectural checks, both required to pass — correct partitioning of one verification obligation across the two mechanisms actually capable of each half, not a downgrade of either.

    **Two tracked, not-yet-built build tasks, both required before Layer 3's own live wiring (item 20) makes a meaningful CP3 run:**
    1. **Create the `customqa:*` Sonar profile** — a real, exportable SonarQube quality profile activating `java:S138` at `max=40` (plus whatever else the profile should carry), versioned in the tracked baseline per ADR-0037 Recommendation 3, and imported into whatever server CP3 targets (closes item 18's own original gap, for the Sonar-expressible subset).
    2. **Build the `direct-webdriver-action` static check in Layer 3** — inspects a generated step-definition class's own package/imports directly for a forbidden `org.openqa.selenium.WebDriver` reference, mirroring D6/CP4's "static, no SUT dependency" posture; wired into CP3 as the second, non-Sonar half of its composite gate.

    Sequencing, stated explicitly: until both land, Layer 3's stage-15 wiring (item 20) would produce a CP3 verdict that is honestly INCOMPLETE by this ADR's own now-corrected story — Sonar alone (against a profile that doesn't exist yet, or against `Sonar way`) was already known-wrong (item 18); a CP3 that ran Sonar without the static check would ALSO be incomplete, silently missing the architectural half entirely. Neither build task is started by this revision.

## 5. How to use this page

- To find out whether a specific decision is locked, find its row above and read its own ADR — this page's summary is not a substitute for the ADR.
- To find out what remains open before a given layer can be built, read that layer's TBD column entries and §4's consolidated list.
- This page is updated whenever a future ADR changes, supersedes, or resolves a TBD item recorded here — by adding a row (new decision), editing a row's Status/TBD columns (a decision changed or a TBD resolved), or adding a note under §3 (a non-ADR state change, like a status-line edit or a register update).
